## 1. 目标、确认规则与权限边界

### 1.1 本次要交付什么

1. 整个资源站取消邀请码注册，改为“邮箱验证码 + 用户名 + 密码”注册。
2. 同时退出原有认证码兑换制度，避免兑换旧码成为新版资格的旁路。
3. 旧账号保留，支持登录后验证并绑定邮箱；增加找回密码、换邮箱和可靠会话撤销。
4. 新版作弊工具箱由服务器判定权限：解谜或者爱发电赞助，两种方式均记录到账号。
5. 赞助价格为 **35 元/赛季**，赛季在后台手动切换。
6. BepInEx 独立底座和单 DLL 插件均在站点的 **工具** 体系发布；网页浏览、下载和客户端安装使用同一份发布数据。
7. 客户端提供底座安装、插件安装/启停/更新/回滚/卸载、冲突检测和损坏检查。
8. 受限文件在真正返回字节的 CDN 层验权，不能只在网页或 API 层隐藏按钮。

### 1.3 必须明确的现实边界

- 邮箱验证只证明当时可读取该邮箱，不等于实名、一人一账号或购买资格。
- 前端配置、显示状态、旧 `is_trusted`、解密成功、安装标记均不能证明服务器权限。
- 可独立运行的底座和 DLL 一旦下载到用户电脑，服务端不能可靠收回其副本，也不能阻止复制。XOR 是教育谜题，不是防破解加密。
- 不因换季/退出登录/邮件故障自动删除、卸载或停用本地插件。无资格仍能查看已安装状态、停用、卸载和用本地备份回滚。
- 如未来要求“无当季资格连本地运行也不能”，需要另行改造 DLL/底座并讨论离线运行、故障降级与 DRM；这不属于本计划默认为已实现的能力。
- 不新增隐蔽反检测、封禁规避、任意远程代码执行、任意游戏进程注入能力；新功能聚焦账号、分发和用户明确选择的文件管理。

## 3. QQ SMTP 研究结论与部署方案

### 3.1 已核实的能力

QQ 邮箱官方帮助说明第三方客户端使用专用授权码；官方 Windows 配置指南列出 `smtp.qq.com`、465/587 和 SSL/TLS。授权码的管理与失效流程见官方帮助。[R1][R2]

本项目选择：

| 配置项 | 方案 |
| --- | --- |
| 发件主机 | `smtp.qq.com` |
| 端口/方式 | **465 + 从连接开始的 TLS**；一期不做明文或自动降级 |
| 登录账号 | 专用通知邮箱的完整地址 |
| 登录密码 | SMTP 专用授权码，**不是 QQ 登录密码** |
| From/信封发件人 | 与实际授权发件账号一致，显示名可用“LCTA 账号服务” |
| 服务端实现 | 标准库 `smtplib.SMTP_SSL`、`ssl.create_default_context()`、`EmailMessage` |
| 网络超时 | 建议 10 秒；可配置，不能无限等待 |
| 邮件格式 | UTF-8 纯文本 + 简洁 HTML，两者内容一致，无附件 |
| 支持的收件人 | 默认各合法邮箱，不限定 `@qq.com` |

Python 官方文档区分 SMTP_SSL 与 STARTTLS；本计划使用 SMTP_SSL 的 465 路径，代码按后端实际 Python 3.11+ 兼容编写，不照抄只适用于更新版本的参数。[R3]

不把 587 是否采用某种升级协议写成无需测试的承诺；如果之后增加替代模式，必须明确协议、验证证书并独立联调。只发送邮件，不需要实现 POP3/IMAP 收件逻辑。

### 3.2 运营准备

1. 使用单独的 QQ 通知邮箱，不用个人主邮箱长期发验证码。
2. 管理员在 QQ 邮箱官方设置中开通相应服务并生成授权码；操作入口按 [R1] 和当时页面为准。
3. 密钥只经部署机环境变量/密钥管理配置；不能放进仓库、工单、聊天、前端、客户端、截图或完整异常日志。
4. SMTP 授权码重置后更新部署配置，并对指定测试邮箱发一封测试邮件。
5. 检查部署主机出站 465 的 DNS、连接、证书、登录和收件表现。没有授权码时只完成 mock 测试，不能声称真实送达已验证。
6. 一期不承诺 QQ 个人邮箱的固定日配额或投递 SLA；当前查到的官方配置文档没有可据此承诺的统一业务发送额度。
7. 配置项目自己的速率/日上限，监测退信、拒发和长时间排队；先做小规模试运行，再调整。
8. SMTP 接受邮件只表示接收了发送请求，不表示进入了收件箱；用户端给出垃圾箱/延迟提示，后台记录 accepted 而非 delivered。

## 4. 邮箱注册、旧账号兼容与邀请码退出

### 4.1 新用户完整流程

1. 在注册页填写邮箱并点击“发送验证码”；可先填写用户名，密码不进入邮件发送任务。
2. 服务端规范化邮箱、检查注册开放开关、执行持久化限流与必要的人机校验。
3. 创建随机 challenge_id，生成验证码，保存安全摘要，把邮件任务写入同一数据库事务。
4. 返回通用提示“若该邮箱可用于本次操作，验证邮件将发送”，并返回 challenge_id 和冷却秒数；不泄露该邮箱是否已注册。
5. 用户填写验证码、用户名、密码及确认密码，提交注册。
6. 服务端校验 purpose/register、邮箱、挑战有效期、尝试次数及验证码；验证码成功后才创建账号。
7. “消费验证码 + 插入用户 + 邮箱唯一性 + 初始会话”在同一事务完成；并发请求不能创建重复邮箱账号或多次消费验证码。
8. 注册成功自动登录，但**仅得到普通账号，不得到当季工具箱资格**；跳转解锁说明或返回原页面。

发送验证码之前不预创建 User，避免大量未验证账号占据用户名/邮箱。前端校验只是提示，服务端 schema、唯一约束和事务才是最终防线。

### 4.2 邮箱规范化和密码策略

- 复用已安装的 `email-validator` 做格式解析；首期支持常规邮箱地址，完整保留可展示地址。
- email_normalized 采用明确的产品策略：去首尾空白、域名标准化；一期邮箱登录大小写不敏感并写清规则。唯一索引使用同一结果，不能前后端各自采用不同算法。
- 不擅自去除 Gmail 点号、`+tag`，不自行合并 QQ 数字地址/别名；一个邮箱账户可能仍有多个地址，不能据此保证一人一账号。
- 拒绝 CR/LF、超长地址、多个收件人、带显示名的列表；发件人、主题和模板是服务端固定的，用户不能指定 SMTP 主机、抄送或任意邮件内容。
- 新注册/重置建议使用 15–128 字符密码，允许中文、空格和密码短语，不强制复杂字符组合，不默默截断；加入常见弱密码拒绝表。旧 8 位起的密码仍可登录，升级时引导而不突然锁号。[R4]
- 当前 RegisterRequest 的用户名规则本身不允许 `@`；迁移仍审计历史/管理员建号。登录使用 identifier，含 `@` 默认邮箱，特殊历史用户名通过显式 username 模式兼容，避免两种查找互相歧义。
- 邮箱原文只在本人/必要管理员接口返回；公开用户资料、评论、资源作者信息不泄露邮箱。

### 4.3 验证码与发信防滥用

**建议初始参数：**6 位随机数字；10 分钟有效；同邮箱/用途 60 秒冷却；每挑战最多 5 次错误。各值可配置，但不能由请求体随意调大。

实现要求：

1. 使用 `secrets` 生成验证码；不使用时间戳或普通伪随机。
2. 只保存 HMAC 摘要，例如 HMAC(server_pepper, version + purpose + challenge_id + normalized_email + user_id + code)。字段采用明确分隔或长度编码；比较用 constant-time。
3. 六位码空间小，**不能只存无服务器秘密的 SHA256(code)**。pepper 与 JWT/CDN/outbox 密钥隔离。
4. challenge 绑定用途、邮箱与目标账号；register 的码不能 reset/bind/change，A 用户的码不能更改 B 用户。
5. 成功消费用条件更新保证一次性；错误次数增量也原子化。注册事务失败时不能误消费有效码。
6. 新挑战取代旧挑战；取消旧的未发送任务；发信 worker 再次确认挑战未过期/被替代。已被旧 SMTP 请求送出的邮件无法撤回，页面明确以最新挑战为准。
7. 限制 challenge 创建数量、发信次数、校验尝试次数；同时按 IP、邮箱、登录账号、用途与全局配额管理。
8. 不能只用现有进程内限流作为验证码总防线；配额落库，重启/多个进程不绕过。SQL 条件更新预占额度，短事务，不在持锁期间等待 SMTP。
9. SMTP 失败不取消安全冷却，避免攻击者无限调用；管理员测试接口另行严格限制，不能转为公开邮件发送器。
10. 重发也不能重置邮箱级累计猜测预算；增加滚动验证预算，例如同邮箱每小时 30 次，超限短暂停止验证，不永久锁正常账号。
11. 开放注册建议启用可配置人机验证；仅 IP 限制不足以抵御分布式邮件轰炸。共享出口的正常用户可经挑战恢复，不使用永久 IP 黑名单。
12. 对邮箱是否存在的不同分支保持统一状态码和大致相同处理路径；不返回“此邮箱已注册”的未验证查询接口。[R5]

### 4.4 邮件队列、超时与秘密保护

- 使用数据库 outbox + 现有调度器的独立发送任务；SMTP 的阻塞操作在线程/任务中执行，不堵 FastAPI event loop。
- 同一挑战仅一个任务；发送 worker 用租约/原子 claim 防止重复发送。状态：queued → sending → accepted / failed / unknown / expired。
- 为可持久化重试，邮件正文或验证码短期可恢复数据采用独立密钥的 AEAD 加密；摘要与密文分开，AAD 绑定挑战/用途，明确声明 cryptography 直接依赖，不只依赖间接安装。
- 发信结束或挑战到期删除秘密 payload；数据库备份中只保留短期密文，日志中不打印完整邮箱、验证码、密码、授权码或完整邮件内容。
- 确定未投递的临时错误允许有限指数退避重试，例如最多 3 次；认证失败、配置错或永久拒绝不无限重试。
- DATA 提交后的网络超时可能“平台接受了但响应丢失”；标 unknown，不自动换新码。重试最多重复同一 challenge 的同一邮件，不能承诺 SMTP exactly-once。
- 冷却/过期时间从服务端控制；队列过慢导致剩余有效期不足则跳过任务并让用户重发，不发送已过期验证码。
- 管理后台提供脱敏健康状态、积压/接受/失败数、最近分类错误及管理员自测；不显示 SMTP_AUTH_CODE 或 raw payload。
- 默认不启用 smtplib debuglevel；持久化日志及错误收集器同样检查脱敏。

### 4.5 旧账号、绑定、换邮箱、找回密码

| 用户状态 | 允许操作 | 不允许的隐含升级 |
| --- | --- | --- |
| 旧账号、无邮箱 | 原用户名/密码登录；本人重新验证密码后绑定邮箱 | 不凭旧 is_trusted 自动得新资格 |
| 新账号或已绑定旧账号 | 邮箱/用户名登录；邮箱找回密码 | 验证邮箱不等于验证赞助 |
| 旧账号、未绑定邮箱且忘记密码 | 管理员人工恢复，核验历史归属并审计 | 不让任意新邮箱直接认领旧用户名 |
| 邮箱不再可用 | 经账号恢复流程处理 | 不能只凭现存会话就转移邮箱/赞助关系 |

- **绑定邮箱**：有效登录 + 最近密码复核 + 新邮箱验证码；原子检查唯一邮箱，成功后建议撤销其他会话并签发当前新会话。
- **换邮箱**：最近密码复核 + 原邮箱验证 + 新邮箱验证，绑定一个 change 事务；旧邮箱不可用走人工恢复。新邮箱提交成功前旧邮箱仍有效；给旧邮箱发通知。
- **找回密码**：统一请求响应；仅已验证邮箱可找回；reset challenge 成功才改密码；不发送密码；成功后撤销全部会话，不自动登录，发改密通知。[R5]
- **普通改密**：验证原密码；更新 auth_version/撤销会话；用户按新密码重新登录。
- 不把本轮邮件验证描述为每次登录的二步验证；如果以后加入 MFA，需要独立设计。
- 邮箱绑定不改变资源归属、历史上传/评论、用户 ID、旧密码哈希或赛季授权记录。

### 4.6 邀请码/认证码真正退出的范围

- 删除新注册 schema 的 invite_code；新 schema 拒绝残留字段，不能忽略旧字段并在无邮箱校验时注册。
- 移除 `_consume_invite`、`generate_invite_code` 在生产注册/授权路径中的调用。
- `/auth/certify`、后台邀请码生成/兑换等写接口关闭；兼容期可统一 410（code=INVITE_FLOW_REMOVED），不能保留隐藏可用入口。
- 下线注册/登录页邀请码文案、个人认证码表单、管理员发码表单、客户端旧指引、SDK 注册参数及示例。
- 历史 invite_codes 表先保留只读审计/备份，后续版本才评估归档/删除；没有入口能再次消费。
- 旧站点其他 trusted_only 资源为避免误伤可保留旧身份语义；新增认证由管理员显式管理，不再发兑换码。新工具箱不继承该语义。
- 旧客户端如果仍提交邀请码，给出“请升级并使用邮箱注册”，不让用户猜为何登录失败。

## 5. 账号会话与网站/客户端一致性

### 5.1 服务端持久化会话

新增 `auth_sessions`（一条设备会话）与刷新令牌记录/代际字段，User 增 `auth_version`。

- access JWT 含 user_id、sid、auth_version、iat、exp，受保护请求检查数据库账号状态/版本和会话撤销情况；权限也从数据库取，不能信客户端或 JWT 的旧授权字段。
- refresh 保存随机 jti/token 摘要、所属会话、generation、过期与消费/撤销时间；刷新事务原子消费当前代并插入下一代。
- 重启后使用过的 refresh 仍不可再用；多 worker 同时刷新只能一个成功。
- 登录为每个浏览器/客户端创建独立会话，不把同一 refresh token 到处复制。
- 登出当前会话可撤销 sid；改密、账号禁用、恢复账号撤销全部会话；auth_version 更新阻止旧 access 继续访问。
- 个人中心可查看脱敏设备记录并退出设备；不需要采集硬件唯一指纹。保留记录期限可配。
- 改密/找回时同步吊销用户 API Key（默认全部，界面提示重新创建）；邮箱绑定/普通登出不随意删除 API Key。
- 一次会话升级上线可以强制重新登录；兼容旧不带 sid 的令牌的窗口必须明确结束，不能无限兼容导致恢复漏洞。

### 5.2 浏览器和宿主的令牌处理

推荐一期完整闭环，而不是增加第二套互相竞争刷新的 token：

1. 普通网站：refresh 使用 Secure、HttpOnly、SameSite Cookie；刷新/退出校验 Origin/CSRF；access 放内存，页面重载走刷新恢复。
2. 桌面客户端/SDK：专用 client 登录/刷新接口返回 token；客户端 refresh 用 Windows DPAPI（当前 Windows 用户）保护存储，不入 config.json；access 尽量只在内存。
3. 内嵌站点：敏感 API 请求经宿主的有限白名单代理，宿主管理刷新；不把 refresh 写回网页 localStorage。普通浏览器不具备桥，仍走网站会话。
4. 网站登录与客户端登录不共享同一个 refresh。嵌入注册成功后由宿主建立独立客户端会话，具体桥协议一起实现和测试。
5. 前端/宿主刷新都有 single-flight；同一代刷新只能由一个执行者发起，其他请求等待结果。
6. 迁移 `ui_default.mod_mirror.auth` 和网站旧 localStorage：验证/换取新会话成功后清除旧明文；失败要求重新登录。不能持续双写。
7. 会话按服务器 origin 隔离。改变镜像站地址不得向新站发送旧站令牌；生产默认仅 HTTPS。
8. Python 桥检查实际 webview 当前 origin、导航状态、消息结构/操作白名单；仅 source='lcta-mod-mirror' 不算可信证明。postMessage 校验 origin 和 source window，不使用 '*' 投递敏感信息。
9. 爱发电授权用系统浏览器或不暴露宿主高权限桥的窗口；不允许外站导航后继续调用安装/读取凭据桥。
10. 日志/错误弹窗/aria2 命令与调试输出均不得泄露 Bearer、refresh 或完整短期下载票据。

不支持 DPAPI 的开发平台需明确提供安全存储适配或“不持久化、每次登录”的降级，不能悄悄改成明文。SDK 自行承担其安全 token 保存，但不能携带 SMTP/爱发电/下载签名密钥。

## 6. 赛季、授权与谜题设计

### 6.1 事实来源与数据关系

```text
邮箱验证 → 普通账号 → 获取/提交当季谜题 ──→ puzzle 授权 ┐
                   → 爱发电 OAuth 绑定 → 核验订单 → sponsor 授权 ├→ 权限服务
管理员 → 创建赛季 → 配置方案/发布资源 → 手动激活 ─────────────────┘
权限服务 → 当前季工具目录 → 安装清单/短期下载票据 → CDN 验签 → 文件
文件 → 本地暂存/校验 → 游戏关闭/冲突检查 → 备份与事务安装 → 本地管理
```

“认证用户”在新版工具箱中的展示改为“当前赛季已解锁”，API 单独返回 toolbox_access。旧 is_trusted 字段只服务于需要保留的旧站点资源，避免全站一次迁移时意外改变普通 Mod 可见性。

判定公式：

```text
账号有效且会话有效
AND 邮箱已验证（旧账号先绑定）
AND 存在当前活动赛季
AND 存在该账号该赛季至少一条未撤销、未暂停的有效授权
AND 目标工具版本被该赛季发布目录允许
AND 当前请求的认证方式/作用域允许此操作
```

- 谜题与赞助记录并存。撤销一笔赞助不抹掉独立的谜题资格；用户状态由“是否还有任何有效来源”重新计算。
- 后端权限服务统一用于工具列表、详情、安装清单、版本历史和签发票据；同一请求取一个一致的赛季快照。
- 普通用户不能给自己写授予记录；owner、旧 trusted、旧 master 系统账号、开发免密加载都不成为当季资格。
- 管理员通过独立管理入口发布/调试并留审计；若需测试下载，使用管理票据并注明管理用途，不伪装成普通购买。
- 一期季工具箱接口建议只接受用户 JWT/明确的管理员会话；现有 API Key 与 master key 不允许直接获取季工具箱文件。以后开放个人 SDK 下载时必须追加 scope、用户季授权和专门测试，不能默认放开。
- 未激活赛季时 fail-closed：无法解锁或签发票据，界面提示维护，不退回旧认证逻辑。

### 6.2 手动赛季状态机

```text
草稿 → 可发布/配置完成 → 管理员激活（唯一 current_season_id）
当前季 → 切换到新季 → 历史季
```

1. 后台创建 season_id（稳定 ID）、slug、显示名称、价格与谜题版本，不依据时间计算当前赛季。
2. 每季保存爱发电允许方案 ID 列表、价格规则、允许发布版本列表；切换前必须完成发布准备。
3. 激活事务更新唯一的 current_season_id 和 generation，并写审计；不靠多个 is_active 行“碰巧只有一个”。
4. 切换页面预览将影响的用户/发布列表、要求确认，注明“旧季停止新下载授权、本地文件不删除”。
5. 不删除旧季授权，不批量改成失效状态；它们只是因不再是当前季而不适用。
6. 并发切季与授权：challenge/订单绑定明确 season_id，不能按提交时的当前季把旧任务挪到新季。旧季谜题提交默认拒绝，提示重取；旧季订单照常归档但不授当前资格。
7. 短期下载票据在切季前已签发的仍有有限剩余有效期，见第 9 节；UI 和后台不能承诺“毫秒级撤销所有链接”。
8. 切回旧季是新的显式管理员操作并留审计，不等于数据库时间回退；既有历史资格是否恢复按原记录判定。

### 6.3 新谜题，不复用旧万能密钥

- 建议仍以 known-plaintext/XOR 为主题，但成为“获取个人挑战 → 本地学习/破解 → 提交答案 → 服务端授予”的流程。
- 每个挑战绑定 user_id、season_id、puzzle_version、随机 nonce，附独立参数/密文；正确答案不等同于 DLL 解密密钥、JWT、CDN 签名密钥或其他用户答案。
- 服务器保存答案的 HMAC 摘要，用户提交只做本次 challenge 验证；不把整个服务密钥放进谜题素材。
- 首期谜题可下载有限文本/练习包，浏览器与客户端展示一致；发布和答案校验版本绑定，出题失败不能直接授资格。
- 建议挑战 24 小时有效、每挑战 10 次答案错误，并另限账号/IP 获取和提交频率。与邮箱验证码严格分表、分 purpose、分密钥。
- 成功提交原子消费 challenge，并幂等插入 source=puzzle 的当季授权；相同成功请求不重复增记录。
- 换季后旧挑战不能取得新季权限；前端本地“已破解”配置不作任何权限依据。
- 说明：题解/脚本可能被分享，这是谜题路线固有属性；可以降低直接复制答案，但不能保证无法批量解题。
- **仍待确认**：若谜题解锁永久有效，需要明确 permanent scope 和每季资格映射，不把当前季授权表中的 NULL 赛季偷偷当永久通行证。第一阶段不能在此规则未确认时冻结最终生产 schema。

## 7. 爱发电接入：账号归属、35 元核验与防冒领

### 7.1 官方能力与限制

官方文档提供 OAuth2 authorization_code 关联授权，需要平台分配应用 clientID/secret，并以 state 校验回调；code 交换在服务端完成。[R6]

官方开发者文档提供按订单号查询订单、Webhook 和分页历史订单查询；订单有方案、用户、真实付款金额和成功状态等字段。文档提醒回调可能重复/延迟，并建议结合 API。[R7]

必须注意：

- 在此次查到的 Webhook 文档中，没有找到可直接实施的入站回调签名规范。出站 API 的签名算法**不能冒充 Webhook 验签**。
- 不因“看起来像官方 JSON”或用户提交截图而立即授予；Webhook 是同步线索，服务端主动查订单才是证据。
- 文档订单示例没有可据此承诺的准确付款时间字段。不能按收到回调的本地时间给订单分赛季，也不能用赞助者 last_pay_time 推断任意历史订单的支付时间。
- OAuth code 交换示例返回用户身份；不假设它同时提供标准 OAuth refresh_token、任意用户订单读取权限或未记载的 scope。
- 成功订单回调不等于退款事件订阅。本轮不承诺平台一定推送退款或订单状态变化，需实测、人工撤销和后台审计补足。

### 7.2 账号绑定与防订单冒领

1. 用户先完成本站邮箱验证并登录，点击“关联爱发电”。
2. 服务端生成随机 state，短期存储并绑定本站用户、会话、目标操作和回调地址；不可由前端指定任意 redirect_uri。
3. 打开官方授权页；回调校验 state 单次消费、有效期、原会话/账号上下文与固定 HTTPS 回调域。
4. 服务端交换 code 得到平台用户 ID；原始 code/client secret 不进日志或客户端。
5. 创建 provider='afdian' 外部身份；同一平台用户仅绑定一个本站账号，一个本站账号一期只绑定一个爱发电身份。
6. 用户提供订单号或点“刷新赞助状态”；服务端查询订单，订单赞助者必须等于该账号已绑定的外部身份。
7. 单笔订单有全局唯一约束，同一订单不可被多账号领取，也不能随解绑重新消耗；本站 user_id 和原始归属保留审计。
8. 解除/改绑需要最近密码复核，并评估已有关联订单；默认不给“解绑即转让资格”。人工合并账号须管理员核验、唯一性与授权转移审计，不是普通按钮。
9. 不以昵称、邮箱文本、订单留言或用户_private_id 的猜测对应来建立归属。先使用官方返回可对应的 user_id；若生产回包要求别的稳定字段，联调后固定规范。

**登记依赖：**需要站长向爱发电申请/登记应用名称与可信域名，取得 clientID/clientSecret，另配置创作者 user_id/API token。OAuth 应用凭据和创作者订单 API token 是不同东西。

未取得 OAuth 凭据时：可以开发 mock 流程并提供**管理员人工核验授予**作为上线过渡，但不能声称“订单号自动解锁已安全实现”。留言验证码方案只能另行评估，不默认把它当与官方账号授权等价的强归属证明。

### 7.3 订单对应赛季与金额规则

**优先建议：每季配置可区分的独立方案 ID → season_id 的固定映射。** 底座和 DLL 可跨季复用，赞助方案映射不能跟着当前季指针随意改写。

核验条件：

- 订单由本站服务器使用本创作者凭据在官方 API 查询得到。
- status 为官方成功态；外部身份一致；plan_id 属于本季白名单。
- 真实付款金额 total_amount 用 Decimal 校验并转整数分，不能用浮点，也不能用显示金额 show_amount 或累计赞助额当实付证明。
- 建议规则：单笔真实付款金额 ≥ 3500 分；零元兑换、其他计划、自选赞助、少付、多个小额累加默认不自动授予，除非后台专门配置并审核。
- 一笔更高金额/多个月份付款默认只解锁该映射季，不预生成未来季权限；月份不能替代管理员指定的赛季。
- 允许展示待核验/已归属历史季/金额不符合/需人工审核等状态，但不向未绑定他人暴露订单详情。

如果必须长期复用同一 plan_id：需要官方实际回包中可验证的时间/季区分信息，或站长逐笔确认订单归季；无法可靠分季时走人工审核，不能猜测。这是服务上线前的业务阻塞项，不在文档中虚构一个 paid_at 字段解决。

### 7.4 Webhook、同步与幂等

- 回调只接收受限大小的 JSON、限定类型和字段；随机回调路径可降低噪音，但不是正式身份签名。
- 持久化最少必要的事件/订单号 → 返回官方要求的确认结构 → 后台主动查询并对账 → 成功后事务写授权。
- 只有事件已可靠落库才确认接收；重复事件可返回成功，不重复授予。异步核验失败记录重试，不能把恶意 payload 带进权限判断。
- 把查询订单、授权生成和重复消费分离，out_trade_no 唯一约束 + entitlement 来源唯一约束兜底。
- 不保存收货姓名、地址、电话等无关订单字段；归档脱敏必要字段和证据摘要即可。
- 定期分页对账处理漏回调；用户点击刷新和管理员补同步复用同一幂等服务。
- 设同步游标、重试/退避、补扫窗口和人工补单；不只扫“最近一页”然后丢弃更晚到的旧订单。
- 平台不可用时不授予未经核验的资格；已经核实且未撤销的当季资格不因一次 API 超时被清空。
- 退款/违规人工撤销 source=sponsor 的对应授权；有另一个独立 puzzle/admin 授权时重新计算，不误撤全部来源。

## 8. 服务端工具发布体系

### 8.1 工具类别与结构化元数据

仍使用现有工具模型，不新增伪普通 Mod 记录，不进入普通 Mod ZIP 标准化管线。

拟新增字段/实体：

| 层级 | 需要的字段/关系 |
| --- | --- |
| ToolResource | stable_tool_id；resource_kind=runtime/plugin；access_policy=public/legacy_trusted/seasonal_toolbox；toolbox_channel |
| ToolVersion | release_id；版本显示字符串；状态 draft/published/withdrawn；发布说明；兼容声明；安装描述符；schema_version |
| ToolFile | 不可变对象键；size/sha256；artifact_kind=runtime_zip/plugin_dll；主文件关系 |
| 版本依赖 | 插件依赖底座 tool_id/release 范围、其他 DLL、冲突 GUID；首期可仅一层已校验依赖 |
| 赛季发布表 | season_id + tool_id + release_id；是否默认推荐、允许历史下载 |
| 安装描述符 | BepInEx GUID/名称/版本；有限 install_kind；安全文件布局；预期关键文件/哈希；配置文件处理规则 |

对程序插件“启停开关”和 Launcher 的集成配置是两回事：前者移动本地 DLL，后者决定 Launcher 是否检查/准备该功能。不能让同一个 checkbox 同时承载两个含义。

### 8.2 发布流程

```text
管理员创建工具 → 建草稿版本 → 上传暂存对象 → 校验大小/类型/哈希
→ 填依赖/GUID/兼容信息 → 测试安装 → 发布不可变版本 → 纳入季目录
```

- 仅管理员或明确授权发布者能配置 seasonal_toolbox；普通工具投稿者不能自建此 policy 后借 owner 特权读取其他资源。
- 上传主体与安装主体分开：不对上传 DLL 做反射加载或执行；管理员可参考源码/离线元数据读取填写 GUID。
- 发布包按白名单选择，不自动把 `mods` 整目录搬到服务器。
- DLL 版本发布后不能就地替换内容并保留原 release_id/对象键；修复也创建新发布。旧接口的 replace 对已发布受限版本拒绝。
- 先完成存储上传/校验再数据库激活，失败保持草稿；清理孤儿对象也要遵守引用检查。
- 相同 GUID 重复安装、两个工具声称相同目标路径、依赖环、缺依赖都在发布时拒绝。
- 前后端显示兼容信息、危险提示和发布说明；未知兼容性写“尚未验证”，不能凭版本字符串断言可运行。
- 底座发布版本和插件版本独立，不让每个 DLL 包都重复带 45 MB 底座。
- 保留受限资源必须的 license/第三方 notices，发布前核对独立包的再分发范围；不是把许可核验视为代码实现细节。

### 8.3 网站管理与用户页面

- 管理后台拆为账号/邮箱、赛季、授权记录、爱发电核验、工具发布五块；不再出现发邀请码/认证码操作。
- 赛季页提供草稿准备、方案映射、允许发布清单、激活预览与审计。
- 工具页增加“底座 / 插件”筛选和结构化字段；旧普通工具继续使用已有流程。
- 用户个人中心：邮箱验证/换绑/密码恢复、设备会话、爱发电绑定、当前季权限来源、历史解锁记录。
- 用户工具箱页：登录/验证邮箱/谜题/赞助指引；有资格后展示季目录、版本说明、网页下载与“在 LCTA 安装”。
- 无资格可看到公开的产品介绍和价格说明，但受限资源详情、版本清单与文件元数据默认不可枚举；首页/搜索/类别计数也按统一可见性过滤。
- 受限资源后台下载走管理接口；普通用户 owner、mine 接口、评论关联详情、图片管理等也要检查不能侧漏私有目录。
- 图片/介绍附件是否公开由独立白名单决定；不能因 resource 图片是公共前缀就把 DLL 上传到同样公开路径。

## 9. 安全下载、签名清单与 CDN 缓存

### 9.1 两类签名，职责分开

1. **短期下载票据**：HMAC-SHA256（独立密钥、kid 轮换）；只在后端/Worker 存密钥，用来证明允许请求哪个文件。
2. **发布安装清单签名**：建议 Ed25519（后端私钥，客户端可信公钥）；验证安装布局、哈希、发布 ID 来自受信发布者，防止被替换 CDN 数据或本地缓存元数据诱导写文件。

邮箱 pepper、outbox 加密密钥、JWT、爱发电 token、CDN HMAC、发布签名私钥分别管理，不复用一个主密钥。不把任何私钥/下载 HMAC 放客户端。清单签名不是运行期 DRM，也不能防止受信服务器本身被完全攻陷。

### 9.2 请求路径

```text
客户端/网页（账号会话）
→ API：检查账号、邮箱、当季授权、发布状态/归属/作用域
→ 返回签名安装清单 + 独立 POST 签发的短期下载票据
→ CDN Worker：校验票据、路径、有效期、方法
→ 校验成功后读取内部文件缓存，或凭 Worker 存储密钥回源
→ 返回字节，客户端核对清单签名、size 与 SHA256
```

- 新受限对象使用专门前缀，例如 `restricted/toolbox/<tool_id>/<release_id>/<sha256>/<safe_name>`，与既有公开 nexus/user/gh 分开。
- 所有受限输出去掉永久 url、external_url、proxy_url；对象键默认不作公共信息。旧下载 GET 如果保留，仍须鉴权后签发票据，不能让它成为多源旁路。
- 上传/GitHub 同步/文件替换/管理文件浏览/存储 inventory 都必须识别该前缀，不能同步出一个公开别名。
- B2 保持私有桶，Worker 存储凭据最小权限；扫描是否有历史公开桶、旧对象、代理或备份公开路径。代码改对但仍有公开副本，就不算闭环。

### 9.3 票据契约

拟定签名 payload：version、kid、canonical_object_key、tool_id、release_id、file_id、user_id、season_id、scope/download、iat、exp、aud/download_host、允许 GET/HEAD。用固定序列化规范签原始 payload 字节，并绑定请求的规范化路径。

- 建议有效期 300 秒，可配置；允许有限时钟误差，部署主机对时。
- 拒绝重复参数、超长票据、不支持算法/版本、未来异常 iat、过期、跨域、跨文件、篡改路径、路径穿越与双重解码歧义。
- 启动生产配置缺签名密钥时受限下载 fail-closed，不退回公开 CDN。
- GET 与 HEAD 必须同等验权；Range 可用于续传/并发分片，同一票据不是单次使用。
- 网站 Bearer 只发本站 API，绝不透传给 CDN、GitHub、代理源；CDN 只看短期下载票据。
- 票据中的 user_id 用于审计不等于设备绑定；链接在过期前可被复制，这一期不承诺防链接分享。
- 已建立的传输通常不会因票据到期立即截断；到期控制新请求。分片重试需重新向 API 取票据并继续同一 release/hash，不能自动切到“最新”导致文件混合。
- 换季、禁用或撤销后立即停止签新票据；已签票据最多剩余 TTL 内能发起请求，已开始传输仍可能完成。
- 要求更即时的禁用/撤销需 Worker 在线查权或维护强一致撤销机制；KV 延迟和短票据不能宣称瞬时失效。默认不为了理论秒级撤销给每个字节请求增加源站依赖。

### 9.4 缓存不能绕过鉴权

Cloudflare 文档区分 Worker 内 Cache API 与可跳过 Worker 执行的缓存机制；本方案必须保证受限 URL 的请求先执行验证逻辑。[R8]

- 顺序固定：分类前缀 → 规范路径 → 验签 → 查内部缓存 → 回源。**缓存 HIT 也验证**。
- 受限路径不配置“直接缓存返回、跳过 Worker”的规则；全链路在实际下载域名验证，不仅本地测试。
- 内部缓存按不可变 object key/release/hash 键控，不把用户票据作为公开缓存键，也不缓存用户 API 身份响应或签发响应。
- 返回浏览器的受限票据/响应与共享内部对象缓存使用不同头策略；不给浏览器长期可共享的授权响应。
- 拒绝将 cache key 对应内部路径当作另一个无票据公开入口。
- Range 命中用有长度的完整缓存；冷缓存的 206 不能直接 cache.put，需只缓存 200 完整响应或直接流式回源。具体按官方 Cache API 限制实现测试。[R8]
- 删除/紧急下架结合停止签票、对象禁用策略与缓存清除；依赖 edge KV 时注明一致性限制。
- Worker 发布是独立部署步骤。当前文件改动不会自动上线，必须记录部署版本、secret 配置及实际域名 smoke 结果。

## 10. 客户端新版工具箱与本地安装管理

### 10.1 页面组织与旧内容兼容

建议工具箱页面由五个区域组成：

1. **账号/当前季状态**：未登录、邮箱未验证、未解锁、已解锁、服务暂不可达；显示更新时间，不把缓存状态当新下载权限。
2. **解锁**：教育谜题、爱发电关联/赞助/刷新核验；旧 XOR 密钥入口退役，不再把解密成功视为权限。
3. **底座**：未安装、由 LCTA 管理、外部安装/冲突、需修复、兼容性待验证；“检查/安装/修复”，不每次打开重下载。
4. **插件目录**：当前季可获取的单 DLL 工具，展示版本、GUID、兼容性、依赖、更新说明；安装和更新按钮。
5. **已安装**：本地管理独立于服务授权，支持启停/卸载/备份回滚/打开目录/检查损坏；外来插件明确“非受管”。

先做旧功能清点表：伤害倍率、静态数据编辑器、插件独立窗口以及私有注册表中其他功能逐个列保留/替换/退役。DLL 新方案替换的是对应运行实现，不自动意味着编辑器等功能也要删除。

- 新下载/安装的资格门是服务端；原加密内容模块可以继续用于需要保留的本地 UI/工具，但其解密加载不是季授权。
- 新本地管理器放在无需旧 blob 解锁也能调用的公共安全管理层；否则用户过季后连卸载都打不开。
- 私有功能若仍存在，需要同步修改私有仓库 registry/接口文案；没有该仓库写权限或源码时单独标明，不能只改公共壳就宣称全部完成。
- 不能在每次 Launcher 启动时悄悄在线更新可执行 DLL；默认手动更新，自动检查可配，自动安装须明确单独同意并游戏关闭。

### 10.2 单独的工具安装路径

复用普通 Mod 下载器可复用的网络/进度能力，但**不复用普通 Mod 的“永远下载 ZIP → 解到 mod 目录”安装策略**。

| 类型 | 下载产物 | 目标 |
| --- | --- | --- |
| 定制 BepInEx 底座 | runtime_zip | 游戏根的已声明文件；受管核心/运行库目录 |
| BepInEx 插件 | plugin_dll | `BepInEx/plugins/LCTA/<安全工具ID>/<主DLL>` |
| 已停用插件 | 本地移动，无网络 | 游戏根 `.lcta-toolbox/disabled/<安全工具ID>/<release_id>/`，在 BepInEx 加载树之外 |
| 备份与日志 | 本地数据 | 游戏根 `.lcta-toolbox/backups/`、事务 journal；大下载缓存可放 LOCALAPPDATA |

路径是客户端固定的布局策略，服务器只给经过校验的工具 ID、文件名与有限 install_kind；不接受任意绝对 install_path、shell 命令或安装脚本。

BepInEx 官方将安装包放到游戏根，并生成配置/日志；本定制底座另有 LctaBoot 等约定，需要按实际包验证，不直接用通用指南替换定制文件。[R9]

### 10.3 底座安装流程

1. 解析选中游戏目录的真实绝对路径，验证游戏可执行文件/目录结构，检查写入能力和磁盘空间。
2. 取得 signed manifest 与下载票据；核验清单签名及 release/hash 绑定，再下载暂存。
3. 网络结束检查 size/SHA256；缓存命中也必须核对内容。新的下载需要权限，已验证本地备份用于回滚不需要网络。
4. 对游戏目录加互斥锁，检查游戏进程、Launcher 安装任务、文件占用；安装/启停/更新/卸载都要求游戏关闭。
5. 安装前再检查一次，降低“检查完游戏随后启动”的竞态；Launcher 启动与管理器共享锁，提交阶段禁止并发启动。外部手动启动只能检测并中止，不能声称可绝对阻止。
6. 检查 `winhttp.dll`、Doorstop、BepInEx/core、dotnet 等已有状态，识别受管旧版/其他框架/未知修改/其他服务器环境。
7. 无冲突则解压到暂存；核验 ZIP 安全性及清单关键文件。外部框架或未知 loader 需用户确认并备份，不能静默覆盖。
8. 将本次要改的现有文件逐一备份，写入恢复 journal，然后逐文件提交；完成后原子写本地 manifest。
9. 安装失败/进程中断下次启动恢复到安装前状态或明确进入 repair_required，不能留下“显示已安装但只有一半文件”的状态。
10. 不自动执行游戏或 DLL 验证“可用”；提示用户首次运行检查日志。手工游戏实测另列发布验收。

安全解压至少覆盖：Zip Slip、绝对/UNC 路径、`..`、反斜杠歧义、符号链接、Windows junction/reparse point、ADS、保留设备名、大小写重复路径、解压总大小/项数上限、文件布局白名单。既有真实路径也要检查，不只检查 ZIP 内字符串。

已有手动装的相同版本可通过哈希验证后**显式接管**；接管之前标非受管，不自动承诺可安全卸载。保留其原始配置和原始备份，不将别人的文件归成本站安装所有权。

### 10.4 DLL 安装、启停、更新与回滚

- **安装**：验证底座依赖、游戏兼容、GUID 唯一性、冲突声明、签名和哈希；游戏关闭后复制入受管独立目录。
- **启用**：只将当前受管 DLL 从 disabled 移回固定加载路径，检查另一版本/GUID 是否已存在；本地管理允许离线。
- **停用**：DLL 移出整个 BepInEx plugins 加载树；不采用普通 Mod 的 `_disable` 规则，也不只改配置里的 enabled 布尔值。
- **更新**：固定旧/新 release_id，备份旧 DLL 后替换；原本停用的插件更新后仍停用，不意外启用。
- **回滚**：恢复用户选定的本地完整备份，保持启停状态与配置；若需重新从服务器取旧版本，当前资格和发布允许历史版本两者都须满足。
- **卸载**：只移除 manifest 记载且校验归属的 DLL/受管文件；配置文件默认保留，可单独选择清理；未知或用户已改动文件先提示备份/保留。
- **完整性检查**：比较本地哈希、预期布局和文件是否被杀毒隔离；异常显示需要修复，不绕过安全软件或自动关闭杀毒。
- **依赖管理**：先底座后插件；不删除仍被其他插件依赖的底座；检测已启用插件间冲突。
- **非受管插件**：可以列出文件/提示冲突，但默认不自动删除或升级；不能把同名 DLL 当同一 GUID。
- **版本判断**：以不可变 release_id + sha256 为准，版本字符串仅展示，避免 `1.10`/`1.9` 和同版本重编译误判。
- **卸载底座**：默认保留含第三方插件的共享目录；只还原本次改动的 loader/文件，不递归删除整个 BepInEx、dotnet 或用户配置树。

### 10.5 本地 manifest 与恢复状态机

每个游戏目录独立持有 schema_version、规范化 game_root、runtime release、plugin GUID/工具ID、release_id/hash、enabled、受管相对路径、文件原哈希/备份、安装时间、配置保留规则、事务状态。

```text
空闲 → 暂存下载/校验 → 等待游戏关闭/确认冲突
→ 备份 → 提交文件 → 写 manifest → 完成
                       └→ 失败/中断 → 回滚/待修复
```

- manifest 写入采用临时文件 + replace；多文件写入不是天然原子事务，必须有可重放恢复 journal。
- 对同一游戏目录设置跨进程锁，GUI/Launcher/第二个 LCTA 实例都遵守。
- 路径变更不误用另一游戏目录的受管清单；移动游戏后的接管需要重新核验。
- 只允许在已核验 game_root 和管理区内做 move/delete；操作前解析绝对路径，遇符号链接等不确定路径停止。不得通过字符串拼接跨 shell 执行删除。
- 缓存用内容哈希，manifest 不含邮箱验证码、会话/签名私钥；本地文件被修改后重新计算，不盲信旧缓存标记。
- 离线时显示本地状态和“在线资格未刷新”；不允许缓存的 entitlement 开新网络下载，却可本地管理和回滚已有副本。

### 10.6 Launcher 配置和插件生命周期

严格遵守当前 AGENTS.md：

- Launcher 集成复选框只在 `webui/sections/launcher-config.html` 的工作模式配置区；工具箱页只说明和 `goAndShow('launcher-config')` 跳转。
- 动态 registry enabled_key 不写入 `core.js` 静态 configKeyMap；仍经 renderLauncherPlugins 注册。
- 重构后的 cheat_core_status 保持渲染前初始化契约，但“本地可用插件注册”与“当季下载权限查询”拆开。不能因网络不可达或过季连本地管理/配置都消失。
- 私有保留功能仍需 ensure_unlocked 才能加载时，保留明确的本地加载层，不能以 dev-src 免密替代季授权。
- 开关值只经 configManager 保存；风险未同意回滚时同步 pendingUpdates；不建立第二套保存路径。
- 明确同意风险，不绕过既有安全提示；服务不可用不悄悄开启新功能。
- 新 BepInEx DLL 以文件存在/位置决定启停，不再默认走旧 Python HookManager 注入。旧插件生命周期逐项保留/退役，避免两个伤害实现同时作用。

## 11. 拟定数据模型、约束与时间规范

以下是实施蓝图，表名可按代码风格微调，但约束不能省略。

| 表/字段 | 核心内容 | 关键约束/索引 |
| --- | --- | --- |
| users 扩展 | email、email_normalized、email_verified_at、auth_version | normalized_email 唯一；旧账号 nullable；系统账号标记/不可前台登录 |
| email_challenges | 随机 ID、purpose、邮箱、目标 user_id、摘要、过期、错误次数、消费/替代状态 | 索引邮箱/用途/有效期；条件更新一次消费 |
| email_change_requests | 账号、原/新邮箱、两边挑战、完成状态/有效期 | 同次 change 绑定两个验证，不允许跨流程拼接 |
| mail_outbox | challenge_id、模板、加密 payload、状态、重试、lease、分类错误 | challenge+模板去重；queue/lease 索引；秘密短 TTL |
| mail_quota_windows | subject_kind、subject_hash、purpose、window、次数 | 组合唯一；服务端原子预占；邮箱/IP 可用 HMAC 摘要降低暴露 |
| auth_sessions | sid、user_id、client_kind、版本、创建/最后活动/过期/撤销 | user_id/revoked_at；登录建立独立设备会话 |
| refresh_credentials | sid、jti/hash、generation、exp、consumed/revoked | token/jti 唯一；sid+generation 唯一；消费与新增同事务 |
| toolbox_seasons | slug、名称、价格分、puzzle_version、规则快照/版本、创建者 | slug 唯一；活动季由 settings 唯一指针决定 |
| season_sponsor_plans | provider、plan_id、season_id、规则 | 默认 plan_id 不跨季重复映射；多方案同季可支持 |
| toolbox_entitlements | user_id、season_id、source、source_ref、状态、授予/撤销/理由/操作者 | user+season+source+source_ref 去重；查询有效授权索引 |
| puzzle_challenges | user_id、season_id、版本、nonce、答案摘要、exp、尝试/消费 | 随机 ID；一次成功；错误数条件更新 |
| external_identities | provider、provider_user_id、user_id、绑定/撤销时间 | provider+provider_user_id 唯一；账号单 provider 唯一 |
| sponsor_orders | provider+order_no、外部用户、plan、金额分、状态、归属季、核验时间 | 订单全局唯一；不把回调金额作为权威值 |
| integration_events/jobs | 订单线索、状态、重试、来源、核验分类 | 同订单去重/幂等处理；不持久化无关收货信息 |
| season_tool_releases | season_id、tool_id、release_id、推荐/历史允许 | 关联唯一；版本必须属于工具且已发布 |
| tool_install_descriptors | release_id、类型、GUID、布局/依赖/兼容、schema_version、签名 | release_id 唯一；校验可执行安装类型白名单 |
| toolbox_audit_events | 操作者、动作、对象ID、时间、理由、脱敏结果 | 切季、授予、撤销、改绑、恢复、发布均留痕 |
| schema_migrations | migration_id、applied_at | 唯一版本；保证升级重入不会再次乱改数据 |

**统一时间规范：**当前项目 utcnow 使用 naive UTC，与 SQLite 一致。新数据库字段也统一存 naive UTC；JWT/外部 API 时间明确转换；出 API 时序列化成带 Z 的 UTC 字符串。不要把 naive datetime 直接当本地时区生成时间戳。界面可按用户时区展示，但赛季不由时间决定。

**保留策略建议：**过期挑战和密文及时清理；发信/限流记录短期；登录设备与事件日志有配置化期限；订单和授权审计按业务需要保留并限制读取。用户注销时，资源归属沿用站点既有处理，授权/订单审计需保留不再可登录的关联标识，避免删账号后订单能重复冒领。实际隐私告知/保存期限上线前由站长确认。

## 12. API 契约蓝图

统一错误结构建议 `{code, message, request_id}`；迁移兼容现有 detail 显示。邮箱/找回请求不泄露账户存在；resource 受限详情按可见性返回 404；工具箱入口可明确返回 401/403 与解锁引导。禁止 API 把安装路径/所有对象键/原始订单秘密一并返出。

### 12.1 账号接口

| 方法与端点（均 /api） | 请求/功能 | 说明 |
| --- | --- | --- |
| POST /auth/email/request | email、purpose、必要的人机 proof/reauth proof | 统一通用响应；bind/change 要登录及复核；客户端不能伪造目标 user_id |
| POST /auth/register | username、password、email、challenge_id、code | 邮箱校验和账号创建同事务；网站建立 Cookie 会话 |
| POST /auth/client/register | 与 register 相同业务字段 | 共享注册服务与限流；给客户端/SDK 独立 token 会话，无邀请码回退 |
| POST /auth/login | identifier、password、可选显式 identifier_type | 浏览器登录/安全 refresh Cookie |
| POST /auth/client/login | 同上 | 桌面/SDK JSON token；同等口令和风控要求 |
| POST /auth/refresh 与 /auth/client/refresh | 网站 Cookie / 客户端 refresh | 两条认证载体路径，共享原子旋转服务 |
| POST /auth/logout | 当前会话 | 持久化撤销，清 Cookie/宿主安全存储 |
| GET /auth/me | 本人信息、邮箱验证状态 | 不把旧 is_trusted 命名为工具箱资格 |
| POST /auth/email/bind | 新邮箱挑战/验证码、最近复核 proof | 只改本人邮箱；旧账号支持 |
| POST /auth/email/change 与 /complete | 发起变更、原/新邮箱证明 | 绑定同一 change request，两边都验证才提交 |
| POST /auth/password/forgot | 邮箱 | 统一响应和限流；不锁号 |
| POST /auth/password/reset | reset challenge/code、新密码 | 撤销全部会话与 API Key；不自动登录 |
| POST /auth/password/change | 原密码、新密码 | 最近复核、版本递增、会话撤销 |
| GET /auth/sessions；DELETE /auth/sessions/{id} | 查看/退出本人设备 | 不暴露他人会话 |
| POST /auth/certify、旧邀请码写接口 | 不再处理旧码 | 兼容期 410，后续移除 |

可将邮件 challenge 的 purpose 发起分装成专用接口，避免单万能端点堆条件；最终以每个用途的相同校验能力为准。

### 12.3 Python/JS 桥接口

新工具管理可增加 `toolbox_get_status`、`toolbox_list_installed`、`toolbox_install`、`toolbox_set_enabled`、`toolbox_update`、`toolbox_rollback`、`toolbox_uninstall`，统一返回 progress/task_id 和可解释错误。

- JS 传 tool_id/release_id/action 和用户确认信息，不传任意 URL、磁盘目标或脚本。
- Python 自己从可信 API 获取描述符，重新检查权限、路径、游戏运行状态和风险同意。
- 网页“在 LCTA 安装”消息标识 resource_type=tool，并升级 bridge protocol_version；旧普通 Mod 消息保持明确独立分派，不能按文件扩展名猜类型。
- 即使 JS 被改成直接调用 install，也必须经过 Python 检查；本地维护操作则明确不需要在线 entitlement。
- 错误码建议覆盖 GAME_RUNNING、FOREIGN_LOADER、PATH_UNSAFE、HASH_MISMATCH、MANIFEST_INVALID、EMAIL_REQUIRED、ENTITLEMENT_REQUIRED、SEASON_CHANGED、RELEASE_WITHDRAWN、DISK_FULL、RECOVERY_REQUIRED。

| P4 爱发电联调 | OAuth 绑定、订单查询、Webhook 持久化/对账、异常人工处理 | 账号归属验证、真实指定订单对账、重复不重复授予、跨季映射正确 | 应用登记/API凭据、明确方案映射、P3 |
| P5 工具发布与边缘闭环 | 类型/依赖/immutable 发布、季目录、签名清单、受限前缀/票据/Worker | 缓存命中仍验权，所有公开直链/代理旁路关闭，后端/Worker一致 | P3、B2/Worker配置 |
| P6 本地底座/插件管理 | 安全下载、DPAPI、安装 journal、受管清单、启停/更新/回滚/卸载 | 临时游戏目录测试；游戏运行拒绝；冲突不覆盖；模拟崩溃可恢复；无资格可停用卸载 | P5接口稳定、正式白名单包 |
| P7 UI/Launcher/旧内容迁移 | 网站管理组件、客户端新页面、桥协议、保留功能适配、配置迁移与打包 | 网页/客户端同号同季状态一致；Launcher 开关唯一；新 JS 在包内；旧功能去留符合清点 | P2–P6 |
| P8 联合验收与灰度上线 | 测试矩阵、部署切换、邮件/订单/缓存监测、文档与更新日志 | 真实域名和 Windows实测记录、完整回滚演练、小范围发布后再开放 | 所有必需项完成 |

业务代码实施时优先 P1/P2：这是全站账号基础，必须先把注册与恢复做完整。P4 外部登记若耗时，可先做 mock 与管理员审计授予，但自动赞助解锁上线验收仍依赖正式联调，不能用“日后补验签”跳过。

P5 完成前不上传正式受限 DLL 至现有公开工具路径。P6 可以先用本地样本做非执行安装测试，但不能在鉴权/发布签名没闭环时把自动可执行文件下载交给生产用户。

## 15. 数据迁移、灰度与回滚

### 15.1 迁移前

1. 记录根仓库、site、frontend、sdk、客户端及必要私有仓库的当前提交和未提交清单；将本任务差异独立记录。
2. 使用数据库一致性备份（SQLite backup API 或明确停写后复制），不能运行中只复制 mirror.db 忽略 WAL。
3. 在备份副本演练增量迁移、旧号登录、邮箱唯一性、关联数据、重复运行和回滚；不得用生产库跑插入默认 admin 的旧 smoke 脚本。
4. 读取 schema/计数与必要脱敏样本，审计历史用户名/系统账号；设计时不输出邮箱、token 或订单隐私。
5. 预先部署带受限前缀验证的 Worker，并配置独立 secrets，验证未知/无票据受限路径拒绝；此时不开放正式资源。
6. 准备 SMTP 发件账号、官方 OAuth 应用/订单 API、可信回调域和测试订单；没有凭据的项目单列未完成，不影响 mock 开发但影响上线声明。

### 15.2 账号切换

- 用 feature flags 控制 email_registration/toolbox/open_release；后端/前端/SDK 版本明确匹配。
- 旧 users 只增加可空邮箱与版本字段，保留原 ID、密码哈希、上传/评论归属；新用户必须带已验证邮箱。
- 迁移不从 is_trusted、InviteCode、master 或客户端 config 自动生成 entitlement。
- 公告“邀请码与认证码停止使用；旧账号可原用户名登录并绑定邮箱；旧解锁不继承新版资格”。
- 会话升级可安排一次重登；部署时强制新模型后旧 token 不带 sid 的兼容必须结束。
- 小范围验证邮箱注册/找回与会话后开放注册；若 SMTP 暂不可用，展示维护并保留既有普通登录，不复活邀请码。
- 旧邀请码接口统一返回清晰退出错误；前端缓存版本更新，避免老页面继续反复提交旧字段。

### 15.3 资源与客户端切换

- 正式底座/首批 DLL 按发布白名单上传私有受限前缀，核验数据库/API/Worker对象路径一致；不发布到既有公开 gh/user 旁路。
- 默认季先建草稿，完成工具清单、方案映射、谜题版本后激活。
- 客户端先发布兼容服务器的新 UI 与桥；旧 client 注册入口有升级提示，普通 Mod 功能不因新工具模块受损。
- 不批量删除旧本地作弊安装；新管理器只明确接管校验通过的包，未知安装提示人工处理。
- 小范围实测：一个解谜账号、一个指定真实赞助账号、一个普通号、一个旧认证号、一个管理员；网站/客户端/缓存均覆盖。
- 全量开放前明确邮件预算、订单补同步计划和故障联系渠道。

### 15.4 回滚原则

- 第一选择关闭新注册/新资源发布/新票据签发，保留已验证账号、绑定关系、订单/授权审计；本地维护继续可用。
- 不能直接回滚到仍可消费邀请码或无票据下载的新前缀的旧版本。要准备兼容新 schema、关闭新功能但保留安全修复的回退版本。
- 新增列/历史表先不 drop；不能覆盖数据库备份而丢失上线后新账号和付款归属。
- 如必须全量恢复数据库，先停止相关写入、保存切换后的订单/账号增量并人工对账；不能靠重新收回调猜测丢失数据。
- Worker 与后端分开记录版本，回滚任何一边都保持受限路径默认拒绝。旧 Worker 不认识前缀而 404 可以接受，公开放行不可以。
- 紧急文件下架：停签票据、下架发布、按策略删除/禁用对象和清缓存；注明票据 TTL 和已下载副本无法撤回的边界。
- 邮件/下载/发布密钥轮换有 kid 与明确旧密钥退场时间；泄露时拒绝旧 kid，不能为兼容无限保留。
