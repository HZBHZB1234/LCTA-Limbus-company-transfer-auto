# LCTA 前端与交互重构方案

<!-- Last updated: 2026-10-02 -->

> 状态：设计提案，尚未实施。此次允许重写前端、交互与桥接契约，不要求旧配置格式、旧路由或旧 DOM 接口向下兼容。仍遵守仓库的 Launcher 单一配置入口、插件风险门控与发布流程规范。

## 1. 产品方向：从「功能工具箱」变成「游戏准备工作台」

核心目标不是把现有表单换成圆角卡片，而是让用户先表达目的，程序再完成必要步骤。

- 日常用户：打开应用 → 确认游戏状态 → 准备并启动。
- 内容用户：选择汉化/模组/文本外观 → 预览影响 → 应用。
- 创作用户：选文本与翻译服务 → 预览范围和费用影响 → 执行 → 审阅结果。
- 专业用户：通过工具库与诊断详情访问底层能力，不再占据日常主界面。

隐式操作的原则：**隐藏实现步骤，不隐藏影响、费用、权限、风险与失败。**

## 2. 基于当前代码的观察

以下为静态代码审阅结论，不代表已运行桌面窗口进行体验测试。

- `webui/index.html` 有大量平级入口，翻译、下载、安装、CDN、启动器、工具与底层恢复功能共同占据侧栏。
- `webui/sections/dashboard.html` 同时展示一键配置、启动游戏、较长的配置范围说明和多个功能跳转；新用户需要先理解实现组成。
- 下载与安装是独立页面，翻译服务配置又位于另一页面；一个「获得可用汉化」目标需要用户拼接步骤。
- `webui/sections/translate.html` 暴露专有名词文件路径等参数，而用户首先关心的是翻译哪些文本、用什么服务、如何应用。
- `webui/css/base.css` 已有 light/dark/purple 主题变量，但主题同时改变侧栏风格与强调色；组件与扩展布局分别集中在较大的 CSS 文件中。
- `webui/js/core.js` 通过配置键映射、缓存和 pendingUpdates 管理配置；`cheat-shell.js` 已有动态插件注册与风险回滚规则。
- 主窗口、编辑器、下载器和诊断窗口均存在，需要统一设计语言与任务状态，而不仅改主窗口。

## 3. 新信息架构

一级导航控制在六项，设置与帮助固定在底部。

| 一级导航 | 用户看到的内容 | 收纳的现有能力 |
| --- | --- | --- |
| 概览 | 游戏是否就绪、准备并启动、需要处理的事项 | dashboard、welcome 的必要引导 |
| 汉化 | 当前来源、更新、切换来源、导入本地包、翻译工作室 | download、install、translate、notice、config |
| 模组 | 已安装内容、浏览来源、冲突与更新提示 | mod-mirror、相关模组管理；无可靠信息时不虚构版本或冲突 |
| 文本外观 | 规则预览、规则集、编辑与应用 | fancy、quick-editor、rule-editor、llm-fancy |
| 启动设置 | 启动工作模式、自动准备项目、Steam 启动集成 | launcher-config；唯一 Launcher 集成开关入口 |
| 工具库 | 搜索/分类查找低频专业工具 | cdn、resource-updater、speed、input-bypass、toolbox、cheat、metadata-recovery、bank、clean、manage |

全局任务入口放在顶栏，显示正在进行的工作与需要用户处理的失败。无任务时不显示假计数。

设置承载路径、外观、网络策略、翻译账户和数据管理。关于、使用帮助归入帮助菜单。

工具搜索可直接进入专业功能，不要求先打开工具库。元数据恢复、音频重打包等明确专业能力仍可完整访问，不以「简化」为由删除。

## 4. 视觉方案：克制的游戏工作台

推荐：中性石墨底色 + 小面积暖琥珀强调，保留 Limbus 氛围但不复刻游戏 HUD。

### 4.1 设计令牌（初稿，实施时需实测对比度）

| 项目 | 建议 |
| --- | --- |
| 深色底/表面/浮层 | `#14171B` / `#1C2026` / `#242A31` |
| 深色正文/次级文字/分隔线 | `#F2F3F5` / `#A9B1BD` / `#323942` |
| 浅色底/表面/正文 | `#F4F5F7` / `#FFFFFF` / `#1E252D` |
| 浅色次级文字/分隔线 | `#5D6672` / `#D9DFE6` |
| 深色强调色/浅色强调色 | `#E7B66A` / `#805416`；强调按钮文字另设专用反色令牌 |
| 间距 | 4 / 8 / 12 / 16 / 24 / 32 px；以 8 px 为主要节奏 |
| 字号 | 正文 14 px、辅助 12 px、分区标题 18 px、页面标题 28 px |
| 行高 | 中文正文 1.6；信息表格根据密度单独定义 |
| 圆角 | 控件 8 px、常规表面 12 px、重点区域 16 px |
| 控件高度 | 输入 40 px、普通按钮 36–40 px、主要启动按钮 44–48 px |
| 侧栏 | 216 px，紧凑模式 184 px；不采用没有标签的纯图标侧栏 |
| 动效 | 120–180 ms 状态过渡；不使用循环发光、长距离漂移和装饰性粒子 |
| 字体 | 本地系统字体；中文优先 Microsoft YaHei UI，拉丁字符 Segoe UI；日志用系统等宽字体 |

- 深浅主题都完整设计；初始建议跟随系统，用户可明确覆盖。
- 不把「蓝紫」作为第三套结构主题。可将强调色作为独立可选偏好，保持组件层级一致。
- 背景、正文、边框、操作、焦点、成功/警告/错误分别使用语义令牌；禁止业务组件直接散写十六进制颜色。
- 标题依靠尺寸和字重，而不是每张卡片一个彩色图标。
- 每屏只有一个明确主动作；次要动作使用描边/文本样式；危险动作独立分区。
- 用分区与列表组织表单，卡片用于完整对象或有限任务，不把每一个字段包成卡片。
- 图标在正式应用本地打包；不依赖在线图标、在线字体或运行时 UI CDN。

### 4.2 布局

应用壳：侧栏 + 页面标题栏 + 主工作区 + 非阻塞任务入口。

- 1280 px 左右：工作区最大宽度约 1120 px，常规页面两列，表单以单列为主。
- 900–1100 px：收窄侧栏、减少次级并列内容，启动区与详细状态上下排列。
- 更窄窗口：菜单变为可展开导航，表单保持单列，操作栏换行。
- 100%/125%/150%/200% 系统缩放与长路径、长错误信息必须验证；不通过缩小字号解决溢出。
- 概念预览中的移动宽度仅用于验证内容重排，不代表新增移动端产品。

## 5. 关键页面与交互

### 5.1 概览：真正的启动首页

第一屏只回答：游戏找到了吗、汉化可用吗、现在能玩吗。

- 顶部：游戏名称、当前位置和简短状态，路径默认显示目录名，完整路径在详情中。
- 重点区：一个「准备并启动」按钮；不要在同一层放一键配置和启动两个强主按钮。
- 状态区：当前汉化、启动准备状态、最近一次结果。只展示真实可获取的信息。
- 待处理事项：缺少路径/汉化不完整/配置待确认时，展示就地解决动作；全部正常时不堆砌教程。
- 最近活动：用户发起或自动准备的任务摘要，可打开详情；不展示常驻原始日志。
- 首次使用则将重点区替换为简短初始化流程；完成后不再反复显示新手说明。

### 5.2 首次使用：确定意图，而不是填满配置表

1. 自动定位游戏；多候选时让用户选择，找不到才要求选目录。
2. 选择汉化来源（展示来源与更新策略，不在没有依据时标注「最佳」）。
3. 确认启动准备计划：默认只列出必要的汉化准备；额外文本包、美化、预下载等在启动设置中选择。
4. 展示将下载/修改的内容、是否会占用较大空间、是否需要 Steam 集成，再执行。

不在初始化过程中自动开启收费翻译、游戏加速、输入反检测或作弊插件。

### 5.3 汉化：合并获取与安装

将用户动作改为：更新当前汉化、切换来源、导入本地包。

「更新」在授权范围内自动完成版本检查 → 下载 → 校验 → 解包到暂存区 → 校验游戏状态 → 备份 → 应用 → 生成操作记录。

- 下载与安装不再要求用户在两个页面间手动接力。
- 更新中保持旧版仍可识别；新包校验失败不得覆盖旧内容。
- 游戏运行时不替换游戏文件；可后台下载，应用阶段排队等待游戏退出。
- 切换来源明确说明覆盖范围；本地包的格式/目标不明确时停下来询问，不猜测安装。
- 公告汉化变为本页面的子功能，展示同步结果；Launcher 集成开关仍只出现在启动设置。
- 专家详情仍可查看包来源、版本、校验、目录与历史，不强迫日常用户阅读。

### 5.4 翻译工作室：任务创建替代表单堆叠

默认只展示：文本范围、服务、质量/速度策略、输出位置。

- 未配置服务时，就地打开账户设置抽屉，保存并校验后回到原任务，不跳去另一个顶级页面。
- 新账户首次向外部服务发送文本时，说明发送内容；收费 API 在启动任务前提示可能产生费用。
- 可先进行少量样本预览；预览也可能计费，不伪装成免费操作。
- 批次大小、并发、超时、术语文件、提示词等收入「高级选项」。策略提供建议值，真实配置可查阅与覆盖。
- 术语优先使用已有本地词表与可用源；不恢复已废弃的 ParaTranz 独立抓取入口，也不默认调用不可用数据源。
- 结果提供差异审阅和「应用到游戏」。翻译完成不等于可以悄悄覆盖用户自定义文件。
- 没有可靠价格信息时提示「服务商计费，以账户账单为准」，不制造精确金额估计。

### 5.5 文本外观：先看效果，再看规则

先展示规则集及其预览、来源、最近修改，再提供编辑入口。

- 对比预览使用原文/效果两种视图，不用用户先理解 JSON 或 bus 语法。
- 普通模式只露出可解释的规则选项；高级编辑器保留原有表达能力。
- 编辑自动保存为草稿、自动形成变更记录，取消「编辑后还必须手动记录，否则修改丢失」的认知负担。
- 自动保存草稿与应用到游戏是两个不同事件；显式「应用」时进行校验、备份与冲突检查。
- 列出不兼容的规则集，解释原因；不会默默更改用户规则来消除冲突。
- 源页面只说明启动时应用的能力，并提供 `goAndShow('launcher-config')` 跳转；不增加第二套集成开关。

### 5.6 启动设置：只有一个真实配置入口

在「工作模式配置」中按用户目的组织：汉化保持更新、使用选定文本外观、下载所需资源、网络优化等。

可提供「精简准备」「自动维护」「自定义」预设，但：

- 预设是配置编辑动作，不是一套额外状态；最终仍写入唯一的实际配置。
- 切换时先展示差异；更改高风险项必须额外授权，不能由预设顺手开启。
- 已自定义的设置不因升级或首次渲染而被覆盖。
- 每项说明具体效果与详情所在页面；源页面只展示摘要与跳转按钮。
- Steam 启动项写入单独确认，备份原值，提供可见的恢复入口。

### 5.7 任务中心：状态可见，但不打断

常驻顶栏入口 + 页面内当前任务摘要 + 可打开的任务详情抽屉。

- 可切换页面；任务不依赖某个 DOM 元素或弹窗存活。
- 默认显示「正在下载汉化」「校验完成」「等待游戏退出」等语义状态。
- 总体进度无法计算时用不确定状态和阶段名，不用虚假的线性百分比。
- 下载等确定阶段可以展示真实百分比与速度，细节中再显示文件数与原始输出。
- 取消能力由后端上报；不支持取消的提交阶段显示「正在完成安全写入」，结束后可恢复。
- 应用关闭时区分「后台仍可继续」「任务会暂停/终止」；若没有独立后台执行器，不声称关窗后仍会运行。
- 启动完成以实际检测结果为准；只有收到启动请求回执时不能显示「游戏已运行」。

## 6. 哪些操作可以隐式完成

| 操作 | 默认处理 | 边界与反馈 |
| --- | --- | --- |
| 定位游戏、读取现有配置、检查路径 | 自动，优先本地 | 多候选/权限不足时询问；不修改用户目录 |
| 读取缓存、复用有效包/转换结果 | 自动 | 按实际内容与版本验证；可在详情中说明复用 |
| 版本检查、网络连接探测 | 允许策略内自动 | 超时不阻塞整个界面；离线明确显示未检查 |
| CDN 优选 | 启用网络优化后按 TTL 自动 | 不每次重新测速；若会改持久网络设置需在首次授权中说明 |
| 下载与安装汉化 | 用户点击更新/已选择自动更新后自动串联 | 来源透明、校验、备份、游戏退出锁；未选来源不擅自选择 |
| 免费/付费翻译、发送文本到服务商 | 用户授权后执行 | 不自动启用；不悄悄换服务；费用和隐私影响可见 |
| 临时文件清理 | 已定义生命周期内自动 | 不删本地包、草稿和备份；清空用户数据仍需确认 |
| 重试临时网络错误 | 有上限、退避、可停止 | 只对可安全重试步骤；不自动重做收费请求或重复提交 |
| 可选启动准备失败 | 策略允许时降级 | 说明跳过的项目；汉化必需文件损坏不能当成功启动 |
| 写 Steam 启动项、覆盖自定义规则 | 明确确认 | 提供变更范围、备份与恢复入口 |
| 加速、反检测、作弊/注入插件 | 默认关闭，专项同意 | 不由智能推荐或预设开启；不得隐藏风险说明 |
| 下载大体积游戏资源/外部运行库 | 首次展示体积、来源和目的 | 不静默安装任意可执行组件；后续自动行为限定授权范围 |

自动化结果需要有操作记录；「一键」不是不可解释的黑盒。

## 7. 后端任务与状态设计（拟新增，不是当前已有保证）

### 7.1 意图 → 计划 → 执行 → 结果

前端提交意图，例如 PrepareAndLaunch、EnsureLocalization、ImportPackage、TranslateTexts、ApplyAppearance。

后端生成并执行计划；前端不通过多个 API 调用自行拼接业务事务。

- 只读/低风险计划可按已有政策执行。
- 涉及敏感修改、费用与新权限时返回 needs_confirmation，附操作清单。
- 执行计划绑定配置 revision、游戏实例、有效期和授权范围；任何相关变化后重新规划，不执行过期确认。
- 幂等请求键阻止连点与桥接重发造成重复下载、安装或启动。
- 每个游戏实例有写入互斥锁；汉化、规则应用与模组安装共用该锁。
- 游戏运行状态是独立事实，不与任务完成混为一谈。

### 7.2 状态机

`created → planning → needs_confirmation/queued → running → succeeded/failed/cancelled`

额外可表示 waiting_for_game_exit、cancelling、recovering；每个阶段明确是否可取消、可重试和可恢复。

任务记录至少包含：task_id、intent、game_id、配置快照 revision、阶段、当前进度/未知标记、事件序号、用户授权、错误摘要、恢复动作、开始/完成时间。

快照 + 增量事件用于跨页面/跨窗口同步。事件含 task_id 和递增 seq；断线后用快照重建，忽略重复和陈旧事件。

不得将「前端关闭弹窗」当作取消任务。

### 7.3 安全提交与恢复

下载暂存 → 内容校验 → 生成变更清单 → 创建备份 → 安全提交 → 写入操作记录。

- 多文件替换不是天然原子操作，必须设计提交日志与补偿恢复；先做可保证的文件范围，再扩大支持。
- 只在后端可以证明恢复可行时显示「撤销/恢复」按钮，不承诺所有类型一键回滚。
- 崩溃后识别未完成提交；先修复/恢复，再允许下一次写入任务。
- 重试只重跑失败的可幂等阶段；收费服务调用的结果无法确认时让用户决定，避免双重计费。
- 磁盘不足、解压失败、包签名/哈希不符、游戏已运行等有各自的用户说明与可行动恢复入口。
- 日志默认脱敏，不包含密钥和完整认证请求；导出诊断包前展示包含内容。

### 7.4 启动的关键与可选步骤

启动计划将项目分成必需、可选、仅用户主动请求三类。

- 必需：有效游戏目录、可执行文件、选定方案的必要文件与安全状态。
- 可选：非关键公告同步、已授权的网络测速、可延期维护。
- 主动请求：收费翻译、高风险注入、变更 Steam 集成等。

后台准备可以并行，游戏目录写入必须串行。可选项目采用启动预算；预算值与具体分类由实施测试确定，不在设计阶段宣称固定时延保证。

关键项目失败时停在可恢复状态；可选失败允许明确提示后继续。不会把「最新汉化未知」伪装成「已是最新」。

## 8. 前端技术重构

### 8.1 推荐方案

Vue 3 + TypeScript + Vite + Vue Router + Pinia，继续使用 Python/pywebview 作为桌面宿主和执行层。

这是重写建议，而非已经安装的依赖。具体版本在实施时按官方支持范围锁定，不使用未核验的「最新版」版本号。

- 页面组件承载表达，领域 Store 承载可观察状态，BridgeClient 隔离 pywebview，后端承载任务执行。
- 组件间不再通过内联 onclick、全局函数和 DOM ID 绑定配置。
- 放弃旧 configKeyMap 作为普通表单的数据模型；设置由 typed schema 描述验证、默认值和授权级别。
- 保留项目要求的 `configManager` 单一写入门面，但重写内部实现；这不是全量旧系统兼容层。
- UI 原子组件只保留一套基础组件与统一变体；专业编辑器仍按功能需要引入 CodeMirror，不把编辑器状态混进全局配置。
- 第一阶段不新增大型通用 UI 组件库；使用可测的小型自有组件，避免再叠一套主题。

### 8.2 拟议目录

```text
webui/
  src/
    app/                 应用壳、路由、初始化
    components/          按钮、输入、状态、抽屉、确认、任务摘要
    features/
      overview/
      localization/
      mods/
      appearance/
      launcher/          Vue 包装与控制逻辑，不重复定义集成控件
      tools/
      tasks/
      settings/
    stores/              game、config、tasks、accounts、plugins
    bridge/              readiness、请求、事件、错误与运行时校验
    styles/              tokens、基础、布局、组件
  sections/
    launcher-config.html Launcher 工作模式集成控件的唯一模板源
  dist/                  构建产物，生成，不手工编辑
```

Launcher 页面 Vue 包装组件可使用外部 template src 指向现有 `sections/launcher-config.html`，模板改写为响应式绑定；具体构建路径先做最小验证。不另建一份同用途控件。

### 8.3 桥接契约

建议新的请求边界：bootstrap、plan_intent、confirm_and_start、get_task_snapshot、cancel_task、update_preferences、get_plugin_registry。

此处是契约方向，不是要求现在改名所有 Python 方法。先定义结构化数据与领域错误，再按意图收敛桥接。

- await 桥接就绪有超时、重连/重试提示。
- bootstrap 返回游戏事实、配置 revision、权限、任务快照、能力列表；字段不能靠 HTML 存在与否推断。
- TypeScript 类型之外还需要运行时校验；Python 返回错误不会穿透成无结构字符串或随意 evaluate_js。
- 多窗口共享同一后端配置与任务事实；前端事件只投影事实，不成为事实来源。

### 8.4 配置保存规则

- 低风险偏好：验证后自动保存，显示「保存中/已保存/未保存」；失败不得显示已完成。
- 多字段账户、路径变更、收费与安全相关配置：草稿 → 校验 → 明确应用。
- 保存绑定 revision，冲突时合并可安全字段或提示用户，不以最后写入静默覆盖另一窗口。
- 即时开关的乐观反馈允许，但失败后必须回滚并给出原因。
- 风险开关在授权完成前只保留临时意图，不进入持久化队列。
- 编辑器草稿、用户设置、任务快照分别存储，避免一次自动保存把未应用规则写入游戏。

### 8.5 私有插件与 Launcher 集成规范

不将私有 registry 的 `launcher.work.*` enabled_key 写入静态前端映射。

- 渲染 Launcher 插件开关前先调用 `pywebview.api.cheat_core_status()`，完成 ensure_unlocked 与插件注册。
- 用 `configManager.registerConfigKey(checkbox_id, enabled_key)` 动态注册；后续写入经 configManager 唯一路径。
- 若实现中存在 pendingUpdates，风险拒绝回滚必须同步覆盖待写值，防止异步误保存。
- 默认先解锁状态再读注册表，不能依赖用户先打开作弊工具箱页。
- 插件是否可用、已解锁、同意风险、已启用、已在本次启动生效分别表示，不合成一个模糊开关。
- 插件缺失或加载失败只说明真实状态，不通过隐藏入口使用户误以为功能消失。

## 9. 打包与离线运行

以下是未来实施义务，本次方案没有修改构建脚本。

- Vite 产物由本地宿主加载；优先验证现有 pywebview 本地服务能力，不能仅凭浏览器预览就判断桌面可用。
- 建议采用相对资源基址与 hash 路由，并实测多入口、刷新、子窗口和动态模块路径。
- 所有 UI 必需资源本地化；离线能打开应用、读取已有配置与进入工具页。
- 新增 Node 前端构建阶段时同步修改 `build.ps1` 与 `.github/workflows/release.yml`；实际编辑前阅读 `prompts/build.ps1.md`。
- 重写打包也必须检查 `.github/InitCode.py` 的旧 JS 拼接和 HTML 资源重写行为，不能新旧打包相互覆盖。
- 过渡期任何新增 `webui/` JS 仍按仓库要求加入 js_files 并保持脚本顺序；若最终移除旧拼接机制，要同时更新实现、规则和开发文档，而不是悄悄漏打包。
- 完整包、更新包、运行时静态资源一起验证。开发态正常不代表打包态完整。

## 10. 不向下兼容的具体含义

可以删除旧页面组织、全局事件接口、旧样式与 DOM ID 假设，也可以使用新的配置 schema。

但「不兼容」不等于丢失用户文件：

- 新 schema 有独立版本；旧配置先备份并提示重新初始化，不强制制作全量迁移层。
- 密钥、本地汉化包、规则集、草稿与用户备份不因重构自动删除。
- 用户可选择导入支持的数据；不能支持的格式给出说明，不静默解析成错误值。
- 启动项与已安装游戏内容按真实状态重新识别，不能仅因新配置为空就重复安装或覆写。

## 11. 实施路线与交付门槛

| 阶段 | 交付 | 完成门槛 |
| --- | --- | --- |
| P0 设计与契约 | 页面原型、组件规范、意图与任务契约、权限表 | 确定主要用户路径；盘点后端真实能力与缺失项 |
| P1 纵向最小闭环 | 新应用壳 + 初始化 + 概览 + 准备并启动 + 任务状态 | 在真实 pywebview 中完成成功/失败/离线启动场景；UI 不依赖旧 DOM |
| P2 汉化闭环 | 合并下载安装、来源切换、本地导入、恢复记录 | 包失败不覆盖旧内容，游戏运行时不写入，连点不重复执行 |
| P3 启动与内容 | 启动设置、文本外观、模组、动态插件 | 单一配置入口、风险门控、跨窗口同步、写入冲突验证 |
| P4 创作与专业工具 | 翻译工作室、统一编辑器风格、专业工具入口 | 付费/隐私确认、草稿与应用分离、所有既有能力有归属 |
| P5 发布与清理 | 新打包、测试、旧资源移除、文档与更新日志 | 开发态/完整包/更新包一致；离线资源完整；不遗留双配置路径 |

阶段用于降低实现风险，不代表保留旧 UI 的长期兼容；目标是替换而非永久双轨。

未盘点后端接口前不承诺工期。P0 后按任务协调、事务恢复、插件桥接、编辑器与打包五类工作量估算。

## 12. 验收清单

### 用户体验

- 正常日常启动不需要理解 CDN、线程数、文件路径或 API 术语。
- 已完成初始化用户可以从概览直接发起启动，准备阶段无需再切换页面手动接力。
- 首次启动只在缺少必要信息或需要授权时询问；不重复询问已授权的低风险步骤。
- 每个页面只有一个主动作；可选设置没有抢占主要信息层级。
- 失败反馈同时提供原因与下一步，原始日志可按需打开。

### 安全与一致性

- 游戏运行时、并发安装时、磁盘不足时、网络中断时、应用崩溃时，文件写入不会无提示地破坏可用状态。
- 任务中切页、窗口关闭、桥接重连和双窗口编辑有明确行为。
- 风险拒绝、插件自动解锁、首次未访问工具页即进入启动设置、重复点击启动均有回归测试。
- 自动操作有来源、授权和记录；收费、注入、删除用户数据绝不借「智能」绕过确认。

### 视觉与可访问性

- 普通正文按 4.5:1 对比度目标验证；不能仅凭设计令牌看起来清晰就判合格。
- 全键盘访问、可见焦点、标签关联、错误说明、减少动效偏好均覆盖。
- 控件优先 36–44 px 高度；尺寸较小的目标仍需检查间距和实际点击区域。
- 深浅主题、900×650 小窗口、125%/150%/200% 缩放、中文长文案与长路径逐项验证。

### 工程

- Vitest/组件测试覆盖配置状态、任务状态投影与错误反馈；桌面桥接使用可控假数据测试。
- Python 测试覆盖计划有效性、幂等、锁、授权、取消边界与恢复。
- 浏览器自动化覆盖页面流转；另做真实 pywebview 与发布包验收，不能以浏览器测试替代宿主验证。
- 新功能落地时更新 `webui/assets/update.md` 最新版本条目，并更新 `.claude/docs/architecture.md`、`modules.md`、`key-paths.md`、`dev-guide.md` 相应内容与日期。
- 本次仅交付设计，不写功能更新日志、不声称已有新行为上线。
