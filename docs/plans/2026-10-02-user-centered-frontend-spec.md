# LCTA 用户中心前端重构：交互规格与实施方案

<!-- Last updated: 2026-10-02 -->

> 状态：设计，未实现。本文件补充已有 `2026-10-02-frontend-and-interaction-redesign.md`，细化用户旅程、自动化边界、领域模型和验收条件；不覆盖该未提交提案，也不修改现有功能代码。
> 本次不要求旧页面、旧 DOM、旧桥接方法或旧配置格式向下兼容。安全、用户数据保全、Launcher 单一入口、动态插件登记与发布规范仍然有效。

## 0. 设计结论

把 LCTA 从「功能入口 + 配置表单集合」重构为「游戏准备工作台」。

用户负责决定 **想用什么内容、是否自动维护、是否接受风险**；程序负责 **找目录、补依赖、下载、校验、准备、按顺序应用和报告结果**。

核心原则：**隐藏过程参数，不隐藏行为后果；减少点击，不减少控制；一次表达意图，后端负责完成闭环。**

不以「一键配置几乎所有功能」代替默认体验，也不让用户在下载、安装、启动配置三个页面手工接力。

## 1. 现状证据与真正要解决的问题

静态阅读当前工作区后的观察，包含已有未提交修改；尚未运行实际桌面窗口，不能当作用户研究或性能结论。

| 现有实现 | 使用障碍 | 重构决定 |
| --- | --- | --- |
| `webui/index.html` 以技术功能拆分大量侧栏入口 | 用户需要先了解实现才能找到目的 | 主导航按使用场景组织；低频专业能力收进工具库 |
| `sections/dashboard.html` 同时突出一键配置与开启游戏 | 初始化与日常使用混在同一层 | 首次显示准备流程，之后只突出「准备并启动」 |
| `js/features.js:refreshDashboard()` 用 Steam 启动项状态决定启动按钮是否可见 | 没写 Steam 启动项就看不到 LCTA 启动入口 | 「从 LCTA 启动」与「接管 Steam 启动」解耦 |
| `oneClickSetup()` 批量开启美化、调爪、资源预下载等 | 用户获得了自己未明确选择的效果和下载负担 | 删除泛化的一键全开；只启用所选方案的必要步骤 |
| `sections/download.html` 与 `sections/install.html` 分离 | 获得汉化不等于用上汉化 | 一个「获取并应用」意图贯穿全流程 |
| `sections/translate.html` 直接暴露路径、线程、格式、消歧等参数 | 普通用户误入自译、误以为 API 是使用汉化的必需项 | 已发布汉化优先；自译是明确的创作入口 |
| 配置自动保存依赖 `core.js` 的 DOM ID 映射和 pendingUpdates | 控件、持久化和操作状态容易互相污染 | 分离偏好、草稿、执行计划和实际生效状态 |
| `app_api/core.py:browse_file/browse_folder()` 把选择结果写回指定 DOM | 后端认识前端控件，难以重写和跨窗口复用 | 选择器返回结构化路径/取消结果，不修改 DOM |
| `features.js:startGame()` 根据请求返回显示启动成功 | 请求受理不应与游戏进程出现等价 | 明确受理、准备中、游戏运行中、退出/启动失败 |
| 当前有公共工具安装管理与私有作弊解锁两条路径 | 简化导航时容易把本地卸载错误地藏进登录/解锁门后 | 公共已安装管理离线可用，私有功能保留单独风险/解锁状态 |

上述位置用于定位，不保证后续编辑后的行号不变；以函数名/文件名为准。

## 2. 用户心智模型与对象归属

### 2.1 三条主旅程

1. **我只想玩中文游戏**：自动识别游戏 → 选汉化方案 → 确认获取并应用 → 准备并启动。
2. **我想调整游戏体验**：选模组/文本外观 → 看变化 → 应用本次内容；需要自动处理时去启动设置启用集成。
3. **我想制作或修复内容**：进入翻译工作室/专业工具 → 配置任务 → 检查影响 → 执行 → 审阅/导出/应用。

不要求第三类用户走新手教程；允许初始化页「先进入工具库」。不设置一套普通界面和一套专家界面两份控件，采用就地渐进披露。

### 2.2 四种状态必须分开

- **已选择**：用户希望使用这个来源/规则/模组。
- **已保存**：偏好已由后端持久化。
- **已应用**：文件准备或配置变更已经成功提交。
- **本次已生效**：运行中的游戏确实使用该内容；无法证明时显示「下次启动生效」或「待验证」。

例如：勾选模组不是「模组已在游戏内生效」；保存翻译账户不表示已扣费；下载完成不表示安装完成。

### 2.3 新领域对象

| 对象 | 职责 | 不应该装入 |
| --- | --- | --- |
| GameTarget | 规范化路径、可执行文件身份、运行状态、本地安装事实 | HTML ID、展示文案 |
| LocalizationRecipe | 汉化组合、来源、构建结果和应用清单 | Launcher 是否自动运行的重复开关 |
| AppearanceRecipe | 气泡样式、文字规则、替换包、应用顺序 | 收费翻译账户 |
| ModInventory | 文件/内容身份、来源记录、安装状态、兼容性证据 | 没有依据的版本/冲突判断 |
| LaunchPolicy | 启动前自动处理哪些已配置内容、失败策略、启动预算 | 另一份规则详情或汉化来源真值 |
| ToolInstallation | 本地底座/插件、安装/停用/回滚/卸载状态 | 必须登录才能执行的本地卸载 |
| Task / Plan / Grant | 用户意图、执行步骤、事实与作用域授权 | 页面弹窗的存在状态 |
| Account / SecretRef | 服务元数据与后端密钥引用 | 前端可读日志、localStorage 明文密钥 |

汉化来源不是粗糙的「所有来源只能选一个」。支持仓库现有的组合模式，但用语义模型表达：

- 「零协会」「OurPlay」「已发布的 LCTA-AU」「零协会 + LCTA-AU」「本地包」。
- 组合方案声明基底、补充层和覆盖顺序，不把 `LM-G` 等内部枚举暴露给普通用户。
- 只在有可信数据时展示覆盖范围、版本和检查时间；不得声称某个来源始终最好或完整覆盖。
- 所选配方是内容唯一真值，Launcher 只消费它。用户换来源后，下一次启动不能又被启动页另一份模式改回去。

## 3. 新信息架构

一级导航六项；任务入口固定在顶栏，设置/帮助固定在导航底部。

| 导航 | 页面职责 | 二级内容 |
| --- | --- | --- |
| 概览 | 是否能玩、一个主动作、需要处理什么 | 游戏状态、汉化状态、待处理事项、最近结果 |
| 汉化 | 获取并维护可用汉化 | 当前方案、切换、导入、公告；翻译工作室作为二级创作入口 |
| 模组 | 获取和管理内容 | 已安装、浏览镜像、导入、变更/冲突说明 |
| 文本外观 | 预览并调整文字效果 | 样式、规则集、编辑、应用/恢复 |
| 启动设置 | 从这里统一决定自动化 | 汉化检查、模组准备、美化/调爪、网络优化、预下载、Steam 集成 |
| 工具库 | 完整保留低频专业能力 | 网络/资源、音频、CG、Metadata、公共工具管理、高风险工具、诊断 |

- 全局搜索按意图与技术别名共同检索：「更新中文」「安装汉化」「CDN」「Metadata」均能找到对应入口。
- 不把作弊/注入工具重新命名成无风险的「增强体验」。搜索结果同样保留风险标签。
- 游戏加速、输入反检测、私有作弊有各自详细页面和专项授权；启动页只放集成开关。
- 设置分为外观、路径与存储、网络、翻译账户、诊断。清理改为按类别展示大小/影响的存储管理，不再占顶级导航。
- 主窗口承载流程；大文本编辑、音频处理和长诊断保留必要独立窗口，使用同一设计令牌、账户/任务事实源。

### 3.1 Launcher 单一入口的落地规则

重写之后，所有「启动时自动……」集成控件 **仍必须且只能** 定义在 `webui/sections/launcher-config.html` 的「工作模式配置」区域。框架页面加载/编译这一模板，不另造一份同用途控件。

- 源页面只有配置详情、手动操作、只读集成说明与 `goAndShow('launcher-config')` 跳转（可带锚点）。
- 概览可显示「启动前会更新汉化」，但不显示同配置的可编辑开关。
- 首次引导只是提交一次明确的准备意图；不嵌入另一份 Launcher 自动化开关。按需引导用户进入启动设置决定今后的策略。
- 汉化来源、外观规则属于内容页；启动页展示只读摘要并跳转修改，不复制这些表单。
- 气泡类型等内容选项归入文本外观；从下载和启动页删除重复的内容设置，源页面仍保留集成介绍。

## 4. 关键交互闭环

### 4.1 首次运行

**第一步：找游戏。** 自动读取本地 Steam/已有路径并验证目录；只有一个可靠候选可预选，多候选要求确认，找不到才浏览。不递归扫描整个磁盘。

**第二步：选汉化。** 用来源卡描述「维护者/内容组合/网络依赖」，不是代理、ZIP、字体处理表单。已发布包与自行翻译明确分开。可选择暂不安装、先用工具。

**第三步：确认本次准备。** 展示将下载与写入的内容、目标游戏、已知大小或「大小待确认」、是否有已有内容需保留。默认不接管 Steam、不启用美化、不大规模预下载、不调用付费服务、不启用高风险功能。

准备完成显示「可以从 LCTA 启动」。Steam 集成作为可选下一步，仅在启动设置出现；无需为了使用应用先退出 Steam。

### 4.2 日常启动

状态驱动唯一主动作：

| 事实 | 主动作 | 说明/次动作 |
| --- | --- | --- |
| 路径缺失 | 选择游戏 | 显示识别候选 |
| 汉化方案未配置 | 准备汉化 | 另有较弱的「暂不汉化，直接启动」 |
| 本地内容有效 | 准备并启动 | 检查已授权内容，复用有效缓存 |
| 正在准备 | 查看准备进度 | 禁止重复创建同意图 |
| 游戏运行中 | 游戏运行中（非启动按钮） | 查看状态；不自动结束进程 |
| 更新已下载且游戏运行中 | 退出游戏后应用 | 手动操作后排队；不因仅退出游戏就自动重新拉起 |
| 检查更新失败、本地可用 | 使用当前版本启动 | 显示「无法确认是否最新」；按用户策略降级 |
| 必需文件无效/未完成提交 | 修复后启动 | 不绕过安全门当作成功 |

启动流程：保存完成的低风险偏好 → 后端生成计划 → 有新影响则确认 → 并行检查/下载 → 串行提交 → 构建本次启动快照 → 拉起进程 → 观察进程出现 → 更新真实状态。

- 尚未保存的敏感草稿不会被「启动」隐式保存；若与本次意图相关，就地选择使用已保存值或先应用草稿。
- 已开始的任务使用快照；过程中编辑启动偏好只影响下一次。若目标目录/文件身份变化，原计划失效。
- 游戏进程已启动后，取消准备任务不等于杀游戏；「结束游戏」若实现必须是独立的确认动作。
- 可选联网步骤有预算。有效本地内容不因公告更新失败而不能玩；「必须使用最新版本」是用户明确选择的严格策略，不是默认。
- 不同完整性/新鲜度分别显示：`可用 / 不完整 / 未验证` 与 `已检查 / 有更新 / 未检查`。

### 4.3 更新、切换与导入汉化

用户点击「更新当前汉化」，隐式执行：来源检查 → 下载/缓存复用 → 安全解包 → 生成清单 → 校验 → 暂存 → 确认覆盖边界 → 备份 → 提交 → 重新应用已配置外观 → 返回结果。

首次确认建立限定授权（这个目标、来源、已管理目录、无新收费）；后续相同范围可免重复确认。来源、权限或修改范围扩大必须重新确认。

- 本地包拖入应用，先识别文件类型和可能的意图；识别可靠也先显示目标与摘要，不直接落盘。不能识别则列出支持类型，不猜测。
- 外来 ZIP 必须防路径穿越、危险符号链接、异常解压大小。不能仅用扩展名认定可安装。
- 游戏运行中可下载，但应用排队。多包合并/来源切换展示新增、覆盖、移除范围；不碰没有归属证据的用户自定义文件。
- 自计算内容哈希用于缓存身份，不冒充签名或官方可信校验。缺少发布者校验信息时明确说明可验证范围。
- 成功后显示「已应用，下次启动生效」，而不是把手动「安装」按钮留给用户再点一次。

### 4.4 文本外观

先显示「原文 / 预期效果」预览和样式选择，再折叠规则、目标文件、优先级等技术细节。

- 三种互斥气泡用单选，不用三枚需要同步取消的复选框。
- 美化规则、文本替换包统一为有序内容层；选中不等于已应用。
- 若预览只能展示标签/结构变化、不能复现游戏实际字体与渲染，标注「效果示意」。
- 点击「应用外观」时从干净基底重新构建，而不是在已美化文本上反复叠加；基础包更新后重新构建所选外观。
- 「保存规则」与「应用到游戏」分开；编辑器草稿不被自动写入游戏。
- 对不具备可恢复基底的旧/外来内容，先保留快照；不能证明可恢复时不显示「一键撤销」。

### 4.5 自行翻译

路径：汉化 → 翻译工作室。第一次显示两种选择：「使用已发布汉化」/「自行翻译」，关闭不启动任务，选择已发布汉化不携带 API 必填。

任务创建以四个字段开始：文本范围、服务账户、处理策略、输出方式。目标默认草稿包；「完成后应用」是明确选择，仍受游戏退出和提交确认约束。

- 账户缺失时就地打开配置抽屉，保留当前范围/参数；返回后继续原流程。
- 本地输入/术语能可靠推断时自动填充，缺失再询问。自动提取原文属于有影响的任务步骤，不因打开页面就下载大量资源。
- 普通策略映射成可检查的能力与参数。不支持的多阶段/思考/自检选项禁用并解释，不能默默丢弃。
- 首次传给第三方服务前显示数据范围与目标；试译、账户测试也可能计费。
- 价格不可靠则只展示字符/文件数与费用提醒，不伪造金额。取消只停止后续请求，无法撤销已经提交的请求或费用。
- 请求结果不明时标记待核实，不自动重发导致双重计费。已记录的完成单元可恢复利用。
- 完成进入审阅：差异、失败项、术语检查/规则检查结果 → 保存包/重试选定项/应用。整包部分失败不等于全部完成。

### 4.6 模组与工具库

- 浏览镜像 → 选内容 → 看来源、目标与已知兼容条件 → 下载并安装。无元数据时展示「未知」，不杜撰可升级版本。
- 无法可靠判断冲突时只列出实际文件重叠；哈希相同的重复内容与真正覆盖冲突分别提示。
- 装模组可按请求完成必要转换并复用缓存；修改 Launcher 集成仍须转去启动设置，不在模组页添加另一枚开关。
- 游戏运行中对安装/卸载写入排队；只读浏览、下载和草稿编辑仍可用。
- 公共已安装工具的查看/停用/卸载/可证明的回滚，不因离线、赛季资格过期、未解锁私有模块而消失。
- FMOD/FSBANK 等组件需要时显示「缺少处理组件」和下载来源/大小/目的，授权后下载、验证、重试原任务。不要只给一个 DLL 路径让用户自行排错，也不能静默安装不可信二进制。
- Metadata 恢复等专业流水线可以折叠阶段和参数，但必须保留输出目标、运行条件、失败阶段和诊断入口。

## 5. 技术细节的三层披露

**L1 主界面：结果与下一步。L2 详情：来源、范围、授权、恢复。L3 高级：参数、文件、结构化日志。**

| 原术语/参数 | 默认展示 | 保留位置/推断逻辑 |
| --- | --- | --- |
| Launcher | 启动设置 / 启动前准备 | 帮助与高级说明保留技术别名 |
| `LM-G` 等模式 | 汉化组合的完整名称 | 由内容配方解析，不让用户查缩写 |
| 代理开关、下载镜像 | 下载方式：自动 | 先按来源策略探测，详情列出实际来源；绝不擅自绕开来源安全限制 |
| ZIP/7z、解包目录 | 获取并应用 | 自动选择可支持格式和应用私有暂存区 |
| 哈希/缓存键 | 已验证 / 校验范围 / 已复用 | 校验详情，不虚构真实性保证 |
| CDN 优选、TTL、写 hosts | 网络优化 | 启用前说明持久网络修改/权限；高级保留节点、缓存时间 |
| 并发、线程、重试间隔 | 自动；需要时可选速度策略 | 能力和运行环境决定有效值，用户可在高级覆盖 |
| 术语 JSON 路径 | 术语：自动 / 选择词表 | 优先可靠本地数据；不复活已废弃的 ParaTranz 独立入口 |
| 请求/响应 JSON 格式 | 服务账户与支持能力 | 账户适配器/高级编辑，不任意猜测自定义服务 |
| DLL 路径、工具依赖 | 所需组件状态 | 已知受信组件自动定位，未知组件由用户明确选择 |
| pywebview「已连接」 | 正常时不显示；异常时可重连 | 诊断页提供桥接状态，不占日常首页 |
| 游戏路径 | 游戏名称 + 目录摘要 | 完整路径可复制；变更走验证与明确应用 |
| 源码日志 | 正在下载 / 等待退出 / 如何处理 | 任务详情 → 诊断日志 |

技术标签可隐藏，风险不能换成模糊好听的名称。不能自动推断的内容应询问，不能通过「智能」掩盖无依据的选择。

## 6. 自动化权限分级

| 级别 | 默认行为 | 示例 |
| --- | --- | --- |
| A：本地只读/可复用 | 自动 | 定位目录、读取状态、识别已有包、验证缓存 |
| B：已授权范围内维护 | 意图或既有策略授权后自动 | 下载/应用选定汉化、复用转换、重新应用已选择外观 |
| C：新影响或不可忽略成本 | 计划确认 | 新来源、较大资源预下载、Steam 修改、hosts 修改、外部组件下载、覆盖自定义内容 |
| D：费用/外传/高风险 | 独立明确授权，默认关闭 | API 翻译、将文本发给服务商、加速/反检测/作弊与注入 |

隐式维护操作仍生成活动记录，显示完成范围、跳过原因和可操作失败。不每次弹出正常日志；后台普通完成只更新状态，不抢焦点。

- 首次网络策略说明网络请求范围。没有明确策略时打开应用不下载大包或测速写 hosts。
- 重试有上限、退避并可取消；仅安全可幂等步骤自动重试。
- 清理只处理属于应用、超过生命周期、无任务引用的临时文件。删除草稿、用户包、备份前显示清单并确认。
- 一次性授权不可扩大成「以后允许所有功能」。Grant 绑定目标、来源、范围、权限、有效版本和授权类型。

## 7. 任务系统：隐式操作可信的前提

### 7.1 前后端职责

前端提交 **意图**，后端生成 **计划** 并对 **事实** 负责。禁止前端串联 `download → install → fancy → launch` 作为事务。

建议 Python 增加 application 层：游戏检测、内容配方解析、任务编排、变更日志、授权和锁；复用现有领域能力。模块可按功能拆开，不能把所有编排塞进 `app_api/core.py`。

GUI 与 `launcher/main.py` 共用同一计划执行器和任务事实源；可保留子进程启动方式，但不能在两处实现不同顺序。跨进程锁不能用 JS 标记或仅一个 Python 进程内的 threading.Lock 代替。

### 7.2 桥接契约（拟新增）

```text
bootstrap() -> capabilities, game facts, config revision, task snapshots, accounts metadata
plan_intent(intent, game_id, desired_config_revision, client_request_id) -> plan
confirm_and_start(plan_id, expected_revision, grant_decision, client_request_id) -> task_id
get_task_snapshot(task_id) -> authoritative task state
get_events(cursor, limit) -> ordered events, next_cursor, resync_required
cancel_task(task_id, expected_task_revision) -> accepted / not_cancellable
update_preferences(patch, expected_revision) -> new_revision / conflict
pick_resource(kind) -> selected {path, kind} / cancelled
get_plugin_registry() -> loaded capabilities and plugin metadata
```

首次计划输入仅包含经过验证的领域值，不接受任意函数名、脚本或未验证的任意路径执行。启动流程中的只读/低风险计划可以按既有授权直接执行。

Plan 至少包含：目标身份、配方/偏好 revision、DAG 步骤、修改范围、来源、需要权限、数据外传/费用、已知大小/未知、阻塞条件、可恢复能力、有效期、影响指纹。

`confirm_and_start` 必须重新验证目标、文件状态、游戏运行情况和影响指纹。计划确认后游戏更新或目录改变，不能执行过期计划。

### 7.3 正交状态，不堆一条超长状态机

Task.lifecycle：`draft → planning → awaiting_confirmation → queued → running → succeeded / failed / cancelled / interrupted`。

Task.wait_reason：`none / game_exit / file_lock / privilege / user_decision`。

Task.phase：`check / acquire / validate / stage / commit / prepare_launch / launch / observe`。

Task.cancel_state：`not_requested / requested / cleaning_up / completed / not_allowed`。

Game.process_state 独立：`unknown / stopped / starting / running / exited`。

- 等待退出不等于失败；「已取消请求」不等于取消完成；启动任务结束不等于游戏已退出。
- 取消下载清理未完成文件；提交临界区允许延迟取消直到安全边界，界面说明原因，不假装即时停止。
- 关闭详情抽屉/窗口不会取消；退出应用时明确列出可留后台与会中断的任务，实际实现以宿主能力为准。
- 事件含递增 seq/cursor；重连先拿快照再续增量。事件不是唯一持久化记录；不将任务状态寄托于弹窗或 toast。
- 推送可用时推送，否则从单一桥接模块适度轮询。页面不各自建立重复轮询。

### 7.4 并发、提交与恢复

- 每个规范化 GameTarget 有跨 GUI/Launcher 进程的写锁。汉化、外观、模组与资源写入共享锁。
- 网络下载与只读检查可并行；互相依赖的内容层有明确执行顺序；对游戏写入串行。
- 每次提交记录被管理文件清单、旧哈希、新哈希、备份位置、已提交步骤和补偿结果。
- Windows 多文件替换不能宣称天然原子；提交前检查空间、权限、进程状态，提交中失败按 journal 恢复。
- 重启先检查未完成提交，完成恢复或要求处理，再放行新的写入任务。恢复失败属于阻塞事项。
- 请求幂等键与后端任务去重防止重复启动。收费调用只在能证明安全时重试，否则请求人工决定。
- 不自动杀游戏或 Steam 来突破锁；需要关闭时说清原因并要求用户选择。Steam 的配置变更另有备份与恢复。

### 7.5 错误必须是「发生什么 + 当前状态 + 下一步」

```text
无法下载新版汉化。
当前已安装版本仍可使用，本次没有修改游戏文件。
[重试下载] [使用当前版本启动] [查看技术详情]
```

错误结构：code、user_message、phase、retryable、managed_files_changed、recovery_actions、diagnostic_id。

区分 `network_unavailable`、`insufficient_disk`、`invalid_package`、`game_running`、`config_conflict`、`permission_required`、`commit_recovery_required`、`provider_result_unknown`。

进度已知时显示实际字节/项目；未知时只显示阶段，不用时间动画伪造 0–100%。部分成功保留结果与失败项，不以绿色「成功」抹去失败。

## 8. 前端技术与配置重构

### 8.1 技术方向

沿用已有提案的 Vue 3 + TypeScript + Vite + Router + Pinia 方向，Python/pywebview 继续负责宿主与领域能力。这里推荐的是重构边界，不锁定未经验证的具体最新版本或最低运行时。

正式落地先做桌面构建验证：相对静态资源路径、路由刷新、外部 Launcher 模板编译、独立窗口、离线、打包入口；验证通过后锁定版本。所有必需 UI 资源本地打包，不依赖运行时在线字体/脚本。

```text
webui/src/
  app/                 应用壳、路由、焦点与异常边界
  domains/             game / localization / appearance / mods / launch / tasks
  features/            六个一级页面、账户抽屉与工具子页面
  components/          按钮、表单、确认、状态、任务摘要、详情抽屉
  bridge/              就绪、类型/运行时校验、请求、事件、领域错误
  stores/              后端事实投影、偏好草稿、任务快照；不编排安装事务
  styles/              语义令牌、布局与组件状态
webui/sections/launcher-config.html  唯一 Launcher 集成控件模板
webui/dist/            生成产物，禁止手工修改
```

不保留新旧页面双轨常驻、不继续增加 inline onclick、不把所有旧 DOM ID 搬成框架里的永久兼容层。

### 8.2 保存语义

- 外观偏好、已校验的低风险开关：自动保存，显示「保存中/已保存/未保存」；失败回滚并解释。
- 服务账户、游戏路径、规则编辑、敏感操作：草稿 → 校验 → 明确保存/应用。多个关联字段一次提交。
- 配置有 schema_version 和 revision；跨窗口冲突不能最后写入者静默胜出。
- 任务开始前确认相关低风险保存已落盘；不依赖 500ms 防抖碰巧完成。
- 静态 DOM ID → 配置键映射可由响应式领域模型替代，但 ConfigManager 仍是持久化唯一通道；草稿、计划、运行事实不挤进同一个 config 对象。

### 8.3 私有插件规范不能被框架替换破坏

1. Launcher 页渲染插件前 `await pywebview.api.cheat_core_status()`，先 ensure_unlocked / 注册。
2. registry 的 `enabled_key`（`launcher.work.*`）**不写静态 configKeyMap**。
3. 使用 `configManager.registerConfigKey(checkbox_id, enabled_key)` 动态登记。
4. 持久化经过 ConfigManager 单一路径；change 门控只处理风险同意。拒绝时同步覆盖 pendingUpdates（若仍有此队列），不能异步误落盘。
5. 可用、解锁、资格、风险同意、已选择集成、此次已生效分别显示；切勿把全部合成「已开启」。

新管理器可以重写内部结构，但必须实现上述行为契约；这不是旧 UI 兼容要求，而是现行插件安全/集成规则。

## 9. 视觉与可用性规范

- 克制的游戏工作台：中性石墨/浅色表面、小面积暖琥珀强调；不做发光 HUD、纹理背景和大型装饰图标。
- 一个页面/流程只有一个主动作。危险区、普通配置和创作任务不挤在同一卡片。
- 第一屏能回答「能否启动、当前内容是什么、要处理什么」。详情按需打开，低级日志不常驻。
- 列表组织对象，单列表单组织设置，预览组织效果；减少卡片嵌套与无意义图标。
- 深浅完整设计、默认跟随系统。成功/警告/错误不只靠颜色，搭配文字与图标。
- 设计基准：正文 14px、辅助 12px、间距 4/8/12/16/24/32、普通控件约 40px、主动作约 48px。对比度需实测，不把初稿色值当合格证明。
- 在桌面窄窗口、125%/150%/200% 缩放、长路径/长翻译结果下重排，不压缩成小字；次级信息可以折叠，主动作不能消失。
- 全键盘可用，焦点可见；确认后返回发起控件，编辑草稿切页可保留；避免默认重复模态打断。
- 搜索提供别名，帮助就地说明；配置悬浮说明按 `prompts/tooltip.md` 规则实施，不以 tooltip 承载唯一的风险说明。

交互示意只使用样例状态，无桥接、无网络、无真实游戏修改；不能拿它当已完成的产品实现。

## 10. 不向下兼容的边界与打包要求

可以一次性删除旧路由、DOM 假设、全局事件函数与旧桥接契约；新 schema 不要求自动迁移旧键值。

但是必须：

- 旧配置只读识别并备份，提示新版本重新设置；不要把旧配置解析失败误报为整款应用损坏。
- 用户包、外部目录、密钥、规则、草稿、备份不自动删除；无法导入的格式说明支持范围。
- 对已有游戏内容先扫描真实状态；来源无法确认就标记未知。新的空配置不是覆盖全部文件的理由。
- 旧 Steam 启动项可能指向当前实例、另一实例或第三方；任何修改前展示差异，备份，保留可证明的恢复路径。
- 正式修改构建过程必须同步 `build.ps1` 与 `.github/workflows/release.yml`，编辑前读 `prompts/build.ps1.md`。
- 新 `webui/` JS 加入 `.github/InitCode.py` 的 js_files，顺序对齐 index；最终移除旧 bundle 拼接时同步打包实现与项目规则，不能悄悄漏打包。
- 验证完整包、更新包、多窗口与断网启动；设计阶段不修改编译或发布文件。

## 12. 验收场景（不是已测结果）

1. 新用户没有 API、未写 Steam 启动项，也可完成汉化准备并从 LCTA 启动。
2. 找到多个游戏目录时不自动写错；不存在/身份变化的目录令旧计划失效。
3. 日常准备只有一个主动作；不要求先手动下载再手动安装。
4. 首次默认不启用调爪、美化、资源大下载、加速/反检测/作弊。
5. 每个「启动时自动……」只有 launcher-config.html 中一份控件；其他页只有只读说明/跳转。
6. 换汉化方案后启动消费同一配方，不会由旧模式改回。
7. 离线时显示可用本地内容和「版本未检查」，不是「已是最新」。
8. 游戏运行时只下载/暂存，写入等待；退出后不会未经新意图突然启动游戏。
9. 更新包校验失败、磁盘不足、被占用不覆盖有效旧内容，给出可执行的下一步。
10. GUI 与 Launcher 同时操作同一游戏时只能一个持有写锁。
11. 汉化更新按配方重新应用外观，不会重复叠加或丢掉选择。
12. 点击两次、桥接重发/重连不重复安装、扣费或启动。
13. 已关闭抽屉的任务仍运行，重新打开能恢复完整状态。
14. 请求已受理、游戏启动中、游戏运行中是不同状态；启动失败不显示成功。
15. 网络任务取消与提交临界区延迟取消显示真实语义，不会静默杀游戏。
16. 提交中异常退出后，下次启动能识别 journal 并恢复；恢复失败阻止下一写入。
17. 没有账户时配置抽屉不丢任务草稿；试译和测试的费用提示不遗漏。
18. 服务结果未知时不自动重发；部分翻译失败进入审阅而非伪装全成功。
19. 危险包路径/异常解压大小被拒绝，来源不明包有明确说明。
20. 无可靠元数据的模组显示未知版本/兼容性；冲突提示有文件证据。
21. 赛季资格过期、离线、未解锁私有模块不阻挡公共本地停用/卸载。
22. 新会话直接进 Launcher 页仍显示已解锁插件；拒绝风险后没有待写入 true 值。
23. 配置保存失败或跨窗口冲突不显示已保存；敏感草稿不被启动动作偷偷提交。
24. 长路径、键盘、系统缩放、窄窗口、深浅主题、断网和两个独立窗口均可操作。
25. 导出的诊断不泄露密钥/票据；用户数据不因不兼容重构被自动清理。
26. 源码启动、完整包、更新包分别验证所有懒加载路由与本地资源，新增脚本不漏包。

建议观察完成率、到可用状态的人工决策数、返回查帮助频次、误触收费/危险操作数与可恢复失败比例。先建立基线再定数值目标，不把未经测试的体验指标写成结果。
