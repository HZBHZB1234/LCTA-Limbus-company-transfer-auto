# LCTA 主界面、Launcher GUI 与前后端交互重构计划

<!-- Last updated: 2026-08-06 -->

> 状态：规划完成，等待确认后执行。
>
> 本文件只定义目标、边界、阶段、任务与验收标准；在计划获得确认前，不开始业务代码重构。

## 1. 计划目标

本次工作不是对现有页面进行换色、加阴影或替换控件，而是重新设计 LCTA 的产品模型、人机交互关系、信息架构和前后端契约，使软件从“功能与设置项集合”转变为“围绕用户目标提供判断、建议、预览和执行的一体化工作台”。重构范围同时包含主 WebUI 与 Launcher GUI；两者使用共享的 WebView 前端基础、设计系统、状态模型和任务反馈，但针对“完整管理”和“快速启动”采用不同的信息密度与窗口形态。

最终需要同时解决两类问题：

1. **操作问题**：用户不需要先理解模块、配置文件和内部术语，便能完成安装汉化、更新资源、启动游戏、自动翻译、管理模组等主要任务。
2. **视觉问题**：页面不再由大量同构卡片、表单和按钮平铺组成，而是通过清晰层级、场景化布局、状态表达、内容密度和适度动效建立辨识度。
3. **Launcher 体验问题**：Launcher GUI 不再是附属的 WinForms 进度窗口，而是默认启用、可交互、可恢复、与主界面互通的现代 WebView 启动中心。

## 2. 与既有计划的关系

本计划：

- **取代** `docs/superpowers/plans/2026-07-15-frontend-usability-plan.md` 作为整体可用性重构的主计划。
- **重新排序** `docs/superpowers/plans/2026-07-19-frontend-refactor.md`：Vue 3、TypeScript、Vite、Pinia 仍可作为目标技术栈，但技术迁移必须服务于已经验证的用户流程，不能先机械复刻旧页面。
- 保留既有规则编辑器、游戏加速等专项设计中仍然有效的领域交互，不在本计划中无理由推翻成熟的独立工具体验。

## 3. 当前基线与根因

### 3.1 代码与界面基线

截至 2026-08-06，主 WebUI 具有以下规模：

- 19 个 `webui/sections/*.html` 页面片段。
- 99 个输入类控件。
- 89 个按钮。
- 88 个 HTML 内联事件处理器。
- 15 个主前端 JavaScript 文件，约 12,680 行。
- 148 处 `pywebview.api` 直接桥接调用。
- 主 API 由多个 mixin 和独立窗口 API 暴露，公开方法数量较多，返回结构与任务反馈模式不统一。
- Launcher GUI 当前由 `launcher/gui_progress.py` 使用 WinForms 构建固定尺寸进度窗，通过 `LaunchPipeline` 阶段回调和 `ProgressLogHandler` 更新；`launcher.work.gui_mode` 默认值为 `false`，GUI 仍是可选附加模式。

### 3.2 主要根因

1. **导航按内部功能模块划分**：用户必须先知道“下载”“安装”“管理”“Launcher 配置”“资源更新”等模块之间的关系。
2. **设置先于目标出现**：很多页面先展示参数，再要求用户推断哪个参数能完成自己的目标。
3. **跨页链路过长**：完成一个结果往往需要在下载、安装、设置、Launcher 等页面间往返。
4. **缺少统一状态模型**：前端能显示零散配置值，但无法统一回答“当前环境是否健康”“下一步应该做什么”“这次操作会改变什么”。
5. **缺少操作计划与结果摘要**：多数动作由按钮直接触发，执行前缺少预检和影响说明，执行后缺少统一的成功、失败、重试与恢复入口。
6. **配置与工作流混杂**：高级参数、一次性选择、长期偏好和危险操作常被放在同一视觉层级。
7. **视觉组件语义不足**：大量页面复用相同卡片、表单组和按钮结构，虽然一致，但无法表达主次、进度、风险、推荐和状态差异。
8. **桥接层过于细碎**：前端直接拼接多次 Python 调用，页面承担了本应由后端工作流编排器负责的决策和顺序控制。
9. **Launcher 与主界面割裂**：Launcher GUI 只能显示阶段、进度和日志，无法复用主界面的状态解释、问题修复、自动化配置和任务结果；主界面也无法展示当前 Launcher 会话或直接接管失败流程。

## 4. 产品设计原则

后续设计和代码评审必须遵循以下原则：

### 4.1 结果优先

- 首页和工作台使用用户语言描述目标，例如“让游戏使用最新汉化”“自动更新后启动游戏”。
- 内部模块名、下载源、目录结构和技术参数只在必要时出现。
- 每个核心场景只能有一个明确的主操作。

### 4.2 状态先于设置

- 先展示系统检测到的游戏、汉化包、资源、Launcher、API 和任务状态。
- 再根据状态给出推荐动作、原因和预期结果。
- 不允许首页退化为入口按钮集合。

### 4.3 渐进披露

- 默认只展示完成任务所必需的信息。
- 常用选项放在当前流程中就地完成。
- 高级参数进入“高级选项”或专家模式，但与基础模式共享同一份配置，不创建重复控件和影子状态。

### 4.4 所见即所得

每个会改变文件、配置或游戏环境的操作，都尽可能提供：

1. 当前状态。
2. 目标状态。
3. 将执行的步骤。
4. 将修改的对象。
5. 风险、权限和空间需求。
6. 执行进度。
7. 结果摘要、失败项与下一步。
8. 在领域允许时提供撤销或恢复。

### 4.5 就地完成

- 流程缺少必要配置时，在当前流程内嵌最小配置，不强迫用户跳转页面。
- 复杂配置可以提供“打开高级设置”，但返回后必须保留流程上下文。
- 相关页面之间通过深链接和上下文传递连接，不能只使用无状态导航。

### 4.6 安全默认值

- 系统根据已检测环境生成推荐方案。
- 用户不需要理解每个下载源、重试次数或并发参数才能开始。
- 危险操作必须有影响说明和明确确认，不能与普通主按钮同权重展示。

### 4.7 一致但不单调

- 一致性用于行为、反馈、间距、键盘和可访问性。
- 视觉层级根据内容语义变化：状态概览、主任务、资源对象、编辑器、警告和日志不使用同一种卡片模板。

## 5. 目标用户与核心任务

### 5.1 用户层级

1. **首次使用者**：不知道项目术语，只想让游戏显示可用汉化。
2. **日常玩家**：希望自动更新、启动和维护，尽量不进入设置页。
3. **内容维护者**：需要翻译、专有词汇、文本美化和规则编辑能力。
4. **高级用户**：需要自定义下载源、缓存、并发、目录、Launcher 工作模式和诊断能力。

### 5.2 必须优先优化的用户任务

按实现优先级排序：

1. 检测游戏并安装推荐汉化。
2. 检查更新并让当前汉化达到可用状态。
3. 配置自动维护并启动游戏。
4. 下载、切换、禁用或删除已安装内容。
5. 更新官方 Localize / AssetBundle 资源。
6. 配置翻译服务并开始自动翻译。
7. 应用文本美化、调爪文本和模组。
8. 诊断故障、查看日志、重试或恢复。
9. 通过默认 Launcher GUI 查看启动计划、处理阻塞、启动游戏并在运行期间掌握当前状态。

## 6. 目标信息架构

主导航从“模块列表”改为以下五个一级区域：

### 6.1 首页

回答四个问题：

- 当前游戏与汉化是否可用？
- 是否有推荐操作？
- 是否有运行中或失败的任务？
- 用户现在能否直接启动游戏？

首页主要内容：

- 环境摘要与健康状态。
- 一个根据状态变化的主操作。
- 推荐动作列表，不超过三项。
- 最近任务与失败恢复。
- 启动游戏入口。
- 首次使用时原位切换为引导流程，不再单独维护“欢迎”“快速上手”“首页”三个割裂入口。

### 6.2 工作台

按目标提供流程，而非按后端模块提供页面：

- 汉化游戏。
- 更新与修复。
- 翻译文本。
- 美化与模组。
- 游戏资源预下载。
- CDN 与网络优化。

每个流程共用统一的工作流框架：选择目标 → 环境预检 → 推荐方案 → 选项 → 变更预览 → 执行 → 结果。

### 6.3 内容库

集中管理所有本地内容对象：

- 已下载汉化包。
- 已安装汉化包。
- 模组。
- 文本美化规则集。
- 调爪文本包。
- 缓存与下载产物。

内容库使用对象列表、状态标签、批量操作和详情抽屉，不再为下载、安装和管理分别维护彼此割裂的页面。

### 6.4 自动化

统一承载 Launcher 和长期自动化策略：

- 启动前执行哪些工作。
- 使用哪种汉化更新策略。
- 是否应用模组、文本美化、调爪文本、资源预下载、游戏加速和 CDN 优选。
- Steam 启动命令和当前接入状态。
- 自动化运行顺序与最近一次执行结果。

必须继续遵守 Launcher 集成规范：决定是否集成的复选框只存在于自动化/Launcher 配置区域；源功能流程只显示集成说明和跳转入口。

### 6.5 设置

只存放长期偏好和专家配置：

- 程序与主题。
- 路径与存储。
- 翻译服务账户。
- 网络、代理与更新。
- 高级性能参数。
- 配置导入、导出与重置。

设置页默认显示常用项；专家项可搜索、可折叠，并标明默认值、推荐值和影响范围。

### 6.6 全局任务中心

任务中心不是一级页面，而是始终可访问的全局层：

- 显示运行中、等待、已完成和失败任务。
- 支持取消、暂停/继续（领域支持时）、重试和查看详情。
- 页面切换或窗口最小化后任务状态不丢失。
- 所有长任务采用同一事件和结果模型。

### 6.7 主界面与 Launcher GUI 的关系

主 WebUI 与 Launcher GUI 是同一产品的两个界面形态，不是两个独立配置程序：

- **主 WebUI**：负责首次配置、内容管理、翻译、美化、诊断、设置和自动化策略编辑。
- **Launcher GUI**：负责展示本次启动计划、启动前检查、阶段进度、可处理阻塞、游戏运行状态和本次会话结果。
- 两个界面共享 `ConfigManager`、`WorkspaceSnapshot`、任务系统、主题偏好和自动化计划，不维护独立副本。
- 主界面首页显示正在运行或最近一次 Launcher 会话，并提供“查看启动窗口”“重新运行”“修复问题”等动作。
- 主界面的自动化区域提供 Launcher GUI 的实时预览，让用户在保存前看到启动窗口会展示哪些步骤。
- Launcher GUI 提供“打开完整 LCTA”“编辑启动计划”“查看任务详情”“打开相关设置”等深链接，并携带当前会话、失败步骤或设置项上下文。
- 如果主 WebUI 已打开，Launcher GUI 的“打开完整 LCTA”应聚焦现有窗口并跳转；如果未打开，则创建主窗口并定位到目标上下文。
- Launcher GUI 即使独立启动也能获得完整启动快照，不依赖主 WebUI 先运行。
- 两个窗口同时存在时，通过后端事件和 revision 同步状态，禁止依赖窗口之间直接调用彼此的 JavaScript。

### 6.8 Launcher GUI 的目标状态

Launcher WebView 默认启用，并覆盖以下四种状态：

1. **启动前**：显示本次将执行的步骤、预计影响、已跳过步骤、阻塞问题和“开始/继续启动”主操作。
2. **启动中**：以阶段时间线展示更新、资源预下载、CDN、模组准备和游戏启动；提供当前步骤详情、进度、速度和可取消状态。
3. **游戏运行中**：显示 PID、运行时长、已启用能力、加速状态与快捷键提示；将详细日志收纳到抽屉中。
4. **结束或失败**：显示本次会话摘要、失败步骤、已完成变更、重试、跳过后继续、打开主界面修复和退出选项。

关闭 Launcher GUI 时保留现有语义，但改为一致的 WebView 对话框：游戏运行中可选择“结束游戏并退出 Launcher”“仅关闭 Launcher，游戏继续运行”或“返回”；启动准备阶段关闭时明确说明取消会停止哪些任务。

## 7. 旧页面迁移映射

| 当前入口 | 目标位置 | 迁移方式 |
|---|---|---|
| `welcome` / `elder` / `dashboard` | 首页 | 合并为状态驱动首页与首次使用引导 |
| `download` / `install` / `manage` | 工作台“汉化游戏” + 内容库 | 下载和安装组合为同一动作计划，管理对象进入内容库 |
| `translate` / `config` / `proper` | 工作台“翻译文本” + 设置“翻译服务” | 在翻译流程内完成必要服务配置，专有词汇成为流程能力 |
| `fancy` | 工作台“美化与模组” + 内容库 | 应用流程与规则资产管理分离 |
| `resource-updater` | 工作台“资源预下载” | 保留独立领域能力，接入统一预检与任务模型 |
| `cdn` | 工作台“网络优化” | 将 Cloudflare / CloudFront 技术选择降级为方案详情 |
| `speed` | 工作台“游戏工具” + 自动化 | 手动控制在工作台，Launcher 集成开关只在自动化区域 |
| `launcher-config` | 自动化 + Launcher GUI | 主界面重构为可视化运行顺序与策略配置；Launcher GUI 只消费本次启动计划并提供上下文跳转 |
| `settings` | 设置 | 按常用、账户、存储、网络、高级重组 |
| `clean` | 内容库“存储管理”或修复流程 | 先展示可回收空间与影响，再执行清理 |
| `log` / `test` | 任务详情 / 诊断模式 | 日志与测试不占据普通用户主导航 |
| `about` | 设置“关于” | 降级为次级信息页面 |

## 8. 核心交互规格

### 8.1 首次使用

目标：用户打开软件后，无需阅读长篇说明即可完成第一次有效操作。

流程：

1. 自动检测游戏目录、当前汉化、Launcher 接入和网络能力。
2. 用一句话询问用户目标，默认推荐“安装并保持汉化可用”。
3. 展示推荐方案和最终效果，而非先展示下载源列表。
4. 缺失游戏路径时在当前步骤选择目录并立即重新检测。
5. 执行前显示将下载、安装和修改的内容。
6. 完成后提供“启动游戏”和“启用自动维护”两个后续动作。

验收：从干净配置进入到开始安装推荐汉化，最多需要三次有意义的用户决策，不包含目录选择器中的系统操作。

### 8.2 日常首页

首页主操作根据状态变化：

- 未检测到游戏：定位游戏。
- 无汉化：安装推荐汉化。
- 汉化可更新：更新汉化。
- 存在失败任务：继续处理。
- 状态健康：启动游戏。

首页不展示完整设置表单，不同时出现多个同权重主按钮。

### 8.3 汉化安装与更新

- 将来源、版本、字体、安装目标和覆盖策略组合为一个动作计划。
- 默认方案由后端根据环境与配置生成。
- 用户可展开“更换来源”或“自定义安装”修改方案。
- 下载成功后自动进入安装，不要求用户手动跳转页面和重新选择文件。
- 执行结果显示安装了什么、当前启用对象和可恢复点。

### 8.4 翻译流程

- 先选择待翻译内容和目标，再检查翻译服务是否可用。
- 服务未配置时，在流程内显示最小凭据表单和测试按钮。
- 在执行前展示文件数量、预计批次、模型、关键高级选项和可能的成本提示。
- 高级管线参数默认折叠，并提供预设而不是要求用户逐项理解。
- 翻译日志和诊断窗口从任务详情进入。

### 8.5 自动化配置

- 用可视化步骤列表展示 Launcher 启动前后的执行顺序。
- 每个步骤显示启用状态、依赖、预计耗时和最近结果。
- 用户启用某步骤时，如果缺少必要配置，直接展开最小修复面板。
- 来源页面只显示“加入启动流程”的状态说明与前往自动化区域按钮，不重复开关。

### 8.6 危险操作

删除、覆盖、清理、移动目录、写入 hosts 等操作必须：

- 在按钮文案中描述动作对象。
- 显示影响范围。
- 需要时明确管理员权限。
- 提供不可撤销提示。
- 与普通操作使用不同视觉语义。

## 9. 视觉设计方向

### 9.1 视觉目标

- 保留 Limbus Company 工具箱的深色、工业感和游戏辅助工具气质，但避免直接复制游戏界面。
- 使用“控制台 + 工作台 + 内容对象”的组合语言，不使用全页面同构白色卡片。
- 建立强标题、关键状态、主操作、次要说明和技术详情五级层次。
- 主 WebUI 与 Launcher GUI 使用同一品牌语言；Launcher GUI 更紧凑、更聚焦、更具阶段感，主 WebUI 则承担高密度管理和编辑。

### 9.2 布局层次

- 应用壳：紧凑导航、全局搜索/命令入口、任务中心、窗口级操作。
- 首页：非对称状态布局，突出主任务与健康状态。
- 工作流：固定步骤轨道 + 主内容 + 变更摘要侧栏。
- 内容库：列表/表格与详情抽屉，支持高信息密度。
- 设置：分组导航 + 搜索 + 低密度表单。
- 编辑器类窗口：继续使用高密度专业布局，不强行套用普通卡片页。
- Launcher GUI：采用紧凑垂直时间线、当前步骤焦点区、游戏运行状态区和可收纳日志抽屉，不复刻主界面的侧边栏布局。

### 9.3 组件语义

建立以下不同组件，而不是继续用一个 `setting-card` 覆盖所有场景：

- `HeroAction`：当前最重要的推荐动作。
- `HealthSummary`：环境健康与阻塞问题。
- `WorkflowStep`：有完成、当前、阻塞和跳过状态的流程步骤。
- `ChangePreview`：当前值、目标值和影响对象对比。
- `ResourceRow`：汉化包、模组、规则等内容对象。
- `TaskItem`：进度、速度、阶段、取消和重试。
- `InspectorPanel`：按需展开技术详情。
- `InlineSetup`：流程内完成缺失配置。
- `DangerZone`：危险操作区域。
- `EmptyState` / `ErrorState` / `SuccessState`：带明确下一步的状态页面。

### 9.4 设计令牌

统一定义：

- 颜色：背景层、表面层、强调色、成功、警告、危险、信息、禁用。
- 排版：展示标题、页面标题、区块标题、正文、辅助文字、代码与数字。
- 空间：4/8 像素基础节奏，限制随意 margin。
- 圆角、边框、阴影和模糊：按层级使用，禁止每个容器都同时使用。
- 动效：只用于状态切换、任务进度、抽屉和步骤变化，并支持减少动态效果。

### 9.5 可访问性

- 正文和关键控件满足 WCAG AA 对比度目标。
- 所有操作可通过键盘完成。
- 焦点状态清晰，不只依赖颜色表达状态。
- 图标按钮必须有可读标签。
- 表单错误与任务错误可被屏幕阅读器感知。

### 9.6 暗色主题参考与配色提取

主 WebUI 与 Launcher GUI 的暗色模式可参考 `https://limbuscompany.huijiwiki.com/wiki/首页` 的整体氛围和配色关系，但不得直接复制站点布局、素材或完整样式。

设计阶段需要完成一次正式的视觉取样：

- 记录参考页面的背景、表面、边框、主文字、弱文字、强调色、危险色和装饰性色关系。
- 以深黑/炭灰背景、冷灰金属表面、温暖浅色文字、低饱和金色或橙色强调、深红边框作为候选方向，再通过实际取样确定最终色值。
- 将参考色转换为语义令牌，不允许页面直接散落参考站点色值。
- 确保参考风格经过 LCTA 品牌化处理，并在高对比度、长时间阅读和任务进度场景下保持可用性。
- 主界面和 Launcher GUI 共用基础暗色令牌，但允许 Launcher GUI 使用更强的阶段强调和状态光效。
- 将参考截图、取样色值、对比度结果和最终令牌映射记录到视觉设计规范中。

### 9.7 组件库策略

允许引入 Vue 组件库，但不能让组件库默认外观重新造成“所有页面都一样”的问题。实施前进行短期技术验证，优先评估以下路线：

1. **无样式或 Headless 组件原语 + 自有设计系统**：优先用于 Dialog、Popover、Select、Tabs、Tooltip、Dropdown、Command Palette 等交互复杂且需要可访问性的组件。
2. **支持无样式模式的完整组件库**：用于表格、树、虚拟列表、分页等高成本组件，但视觉必须接入 LCTA 令牌。
3. **完整样式组件库**：只有在主题覆盖能力、包体积和视觉一致性验证通过后，才允许局部使用。

候选可包含 Reka UI、PrimeVue、Naive UI 或实施时同等级的 Vue 3 组件方案。最终选择必须满足：

- Vue 3 与 TypeScript 支持。
- 键盘操作、焦点管理和 ARIA 能力。
- 支持自定义主题或无样式模式。
- 可 tree-shaking，且不会显著放大离线包体积。
- 可完全本地打包，不依赖运行时 CDN、远程字体或远程图标。
- 在 pywebview / WebView2 中行为稳定。
- 同时适用于主 WebUI 和 Launcher GUI，避免维护两套基础组件。

组件库选型必须以一个包含 Select、Dialog、Tooltip、Virtual List 和 Launcher 阶段时间线的原型为依据，不以文档观感直接决定。

## 11. 目标后端架构与桥接契约

### 11.1 新增产品级门面

在现有领域函数之上增加面向界面的产品门面，避免前端理解底层调用顺序：

- `WorkspaceService`：汇总游戏、汉化、资源、Launcher、API、网络和存储状态。
- `RecommendationService`：根据快照生成推荐动作与阻塞原因。
- `WorkflowService`：构建、验证和执行动作计划。
- `TaskService`：统一任务生命周期、进度、取消、重试和结果。
- `LibraryService`：统一列出和管理本地内容对象。
- `SettingsService`：提供分区设置、验证和事务式更新。
- `LaunchSessionService`：将 `LaunchPipeline` 映射为可恢复、可查询、可取消的启动会话，并负责主界面与 Launcher GUI 的状态同步。

领域逻辑继续复用 `webutils/`、`resource_updater/`、`translateFunc/`、`globalManagers/`，产品门面不复制底层实现。

### 11.3 建议桥接 API

第一版统一接口至少包含：

```text
get_workspace_snapshot()

```

接口名可在契约设计阶段调整，但不得继续为每个按钮增加一个无统一返回结构的桥接方法。

### 11.4 任务事件

Python → 前端统一派发事件：

```text
lcta:workspace-changed
lcta:task-created
lcta:task-updated
lcta:task-finished
lcta:library-changed
lcta:settings-changed
lcta:launcher-session-changed
lcta:launcher-window-command
```

事件必须带版本和实体 ID；前端收到未知版本时应降级为重新拉取快照，而不是静默失效。

Launcher 会话事件必须由后端持有真相；窗口重新创建后可通过 `session_id` 恢复当前阶段、日志摘要和游戏运行状态。

### 11.5 配置事务

- 安全偏好允许自动保存，但必须有成功/失败反馈。
- 会影响多个配置项的流程先生成 patch，再一次提交。
- 使用 `revision` 或等价机制防止旧页面覆盖新状态。
- 保存失败时保留草稿并指出具体字段。
- 不再由 Python 通过 `evaluate_js()` 反向要求页面收集整个表单。

## 13. 验收指标

### 13.1 可用性

- 首次安装推荐汉化：最多三次有意义决策。
- 日常健康状态下：启动游戏只需一次主操作。
- Launcher GUI 从启动前检查到游戏运行持续使用同一窗口，不要求用户返回主 WebUI 查看关键状态。
- Launcher GUI 遇到可修复阻塞时，可在当前窗口处理或一次操作带上下文打开主 WebUI。
- 任一核心流程缺少配置时：无需离开流程即可补全并继续。
- 任一长任务：最多一次操作即可打开任务详情。
- 任一失败任务：结果页明确提供重试、修改选项或查看诊断中的至少一个可行动入口。

### 13.2 信息架构

- 普通主导航一级入口不超过五个。
- 首页推荐动作不超过三个，且只有一个主操作。
- 高级配置默认不占据核心流程首屏。
- 相同配置项不在多个页面重复出现。
- Launcher GUI 不复制完整自动化设置，只展示本次计划、最小修复项和上下文跳转。

### 13.3 技术质量

- 业务组件中直接 `pywebview.api` 调用为零。
- 新工作流 API 使用统一成功、错误和任务结构。
- 新长任务全部进入统一任务中心。
- Launcher 使用 WebView 入口，`launcher.work.gui_mode` 默认启用或被新的显示模式配置等价替代。
- Launcher 会话由后端持有，可在窗口重建或主窗口后来打开时恢复。
- TypeScript strict、ESLint、Vitest 和 Python 相关测试通过。
- 首屏通过一个聚合快照完成主要状态初始化，特殊能力检测最多追加少量并行请求。

### 13.4 视觉与可访问性

- 关键文字与控件满足 WCAG AA 对比度目标。
- 所有核心流程支持键盘操作和清晰焦点状态。
- 所有页面具备加载、空、错误和成功状态。
- 不再以同一种卡片和表单布局覆盖所有内容类型。
- 主 WebUI 与 Launcher GUI 暗色模式共享语义令牌，视觉一致但布局不互相照搬。
- 动效不阻碍操作，并支持系统减少动态效果偏好。

## 15. 迁移策略与风险控制

### 15.1 纵切片迁移

不按“先重写所有组件，再一次接入业务”的方式执行。每次迁移一个可完整验收的用户任务：

1. 状态模型。
2. 动作计划。
3. 后端执行。
4. 统一任务反馈。
5. 新界面。
6. 自动化测试。
7. 旧入口下线。

### 15.2 双轨期间的唯一数据源

- 配置仍以 `ConfigManager` 为唯一持久化来源。
- 任务以新 `TaskService` 为唯一运行状态来源。
- Launcher 会话以 `LaunchSessionService` 为唯一状态来源，主 WebUI 与 Launcher GUI 都只消费该服务。
- 旧页面通过兼容适配器读取同一来源。
- 禁止新旧前端分别维护任务队列、配置缓存或安装状态。

### 15.3 主要风险

| 风险 | 控制方式 |
|---|---|
| 大规模重构导致功能回归 | 纵切片迁移、旧 UI 回退、行为等价清单 |
| Vue 构建与打包链不一致 | 早期建立离线构建验证，构建脚本与 CI 同步修改 |
| 前后端契约持续变化 | Phase 1 先冻结版本化数据结构，再开始大量页面实现 |
| 视觉升级但交互仍复杂 | 所有页面必须对应用户任务指标，禁止仅按截图验收 |
| 简化界面损失高级能力 | 基础模式与专家模式共享状态，专业编辑器保留高密度能力 |
| 组件库限制视觉表达或增加包体积 | 先做真实控件原型和打包对比，优先 Headless 原语与局部引入 |
| Launcher 配置重复 | 代码评审检查集成开关唯一位置，源页面只提供说明与跳转 |
| WebView 事件循环与启动管线互相阻塞 | 管线进入受控工作线程，窗口生命周期和取消状态由 `LaunchSessionService` 统一管理 |
| 主窗口与 Launcher 窗口状态冲突 | 后端单一真相、revision、窗口发现和版本化事件 |
| 长任务状态丢失 | 后端持有任务状态，前端通过快照与事件恢复 |
